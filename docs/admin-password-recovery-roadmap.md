## Phase 1 - UAT บัญชี Admin จริง

เป้าหมาย: ยืนยันวงจรครบตั้งแต่ผูก LINE จนกลับเข้าสู่ระบบด้วยรหัสใหม่ โดยใช้บัญชี admin ที่เจ้าของบัญชีอนุญาต

งานอัตโนมัติ:

- [ ] ตรวจ backup ล่าสุด, migration baseline, health และ PM2 ก่อนเปิด flag
- [ ] เปิด `FEATURE_ADMIN_PASSWORD_RECOVERY=true` และ reload backend
- [ ] ตรวจ config endpoint, เมนูความปลอดภัย และหน้า forgot-password หลังเปิด flag
- [ ] เก็บ HTTP status, audit action ID และเวลาประเทศไทยโดยไม่เก็บข้อมูลลับ
- [ ] หลัง UAT รัน unit tests, public gate, postdeploy gate และตรวจจำนวนข้อมูล recovery

งานที่ผู้ทดสอบ admin ต้องทำเอง:

- [ ] เพิ่ม LINE OA เป็นเพื่อนและเปิด LIFF จาก LINE
- [ ] ยืนยัน LINE ด้วยรหัสผ่านปัจจุบัน และตรวจว่าได้รับข้อความทดสอบ
- [ ] ดาวน์โหลด recovery code 8 รหัสและเก็บนอกระบบในที่ปลอดภัย
- [ ] ออกจากระบบ ขอรีเซ็ต รับลิงก์ใน LINE และเปลี่ยนรหัสด้วย code แบบใช้ครั้งเดียว
- [ ] ยืนยันว่ารหัสเดิมใช้ไม่ได้ รหัสใหม่ใช้ได้ และลิงก์/code เดิมใช้ซ้ำไม่ได้
- [ ] ตรวจภาพหลักฐานที่ปิด username, LINE ID, token, password และ recovery code แล้ว
- [ ] เจ้าของบัญชียืนยันผล UAT และอนุมัติว่าจะเปิดใช้งานต่อหรือปิด flag กลับ

เกณฑ์ผ่าน: checklist ใน `docs/ops-admin-password-recovery.md` ผ่านทุกข้อ, ไม่มี Critical/Major defect, audit trail ครบ และไม่มี secret ใน evidence

## Phase 2 - เปิดใช้ Admin และเฝ้าระวัง

เป้าหมาย: เปิดให้ admin ใช้งานจริงอย่างควบคุมได้ก่อนขยายบทบาท

- [ ] คง flag เปิดหลัง Phase 1 ได้รับอนุมัติ
- [ ] กำหนด admin สำรองและช่องทาง manual reset กรณี LINE ใช้งานไม่ได้
- [ ] เฝ้าดู 4xx/5xx, LINE push failure, rate-limit และ audit event อย่างน้อย 7 วัน
- [ ] ตรวจ recovery code คงเหลือโดยแสดงเฉพาะจำนวน ไม่แสดงตัวรหัส
- [ ] ทดสอบขั้นตอนปิดฉุกเฉินด้วย flag โดยไม่ลบตารางหรือ audit log
- [ ] สรุป incident/feedback และตัดสินใจ Go/No-Go สำหรับ Phase 3

เกณฑ์ผ่าน: ไม่พบ Critical/Major defect ในช่วงเฝ้าระวัง และ operator ยืนยัน rollback procedure

## Phase 3 - จังหวัด ต้นสังกัด และขนส่ง

เป้าหมาย: รองรับ `province`, `affiliation` และ `transport` หลังยืนยันรูปแบบเจ้าของบัญชี

Decision gate ที่เจ้าของระบบต้องยืนยันก่อนเขียนโค้ด:

- [ ] แต่ละ username เป็นบัญชีบุคคล หรือบัญชีกลางของหน่วยงาน
- [ ] หากเป็นบัญชีกลาง ใครมีอำนาจผูก/เปลี่ยน LINE และมีขั้นตอนส่งมอบเมื่อเปลี่ยนผู้รับผิดชอบอย่างไร
- [ ] หนึ่งบัญชีผูกได้หนึ่ง LINE เท่านั้น หรือจำเป็นต้องมีผู้รับผิดชอบสำรอง

งานพัฒนาเมื่อ logic ได้รับการยืนยัน:

- [ ] เปลี่ยน allowlist บทบาทแบบ explicit ไม่ใช้เงื่อนไขเปิดทุก role
- [ ] เพิ่ม feature flag แยกบทบาท เพื่อ rollback ได้ทีละกลุ่ม
- [ ] เพิ่ม tests ของ RBAC, scope, enumeration resistance, concurrent reset และ audit log
- [ ] UAT แยกบทบาทอย่างน้อยบทบาทละหนึ่งบัญชีจริง

เกณฑ์ผ่าน: ผู้รับผิดชอบหน่วยงานยืนยัน ownership, UAT ผ่าน และปิดบทบาทหนึ่งได้โดยไม่กระทบบทบาทอื่น

## Phase 4 - โรงเรียนและบัญชีย่อยครู

เป้าหมาย: ให้ `school` กู้รหัสได้โดยไม่ทำให้บัญชีกลางหรือขอบเขตชั้นเรียนถูกยึดโดยบุคคลเดียว

Decision gate:

- [ ] บัญชีหลักโรงเรียนผูกกับ LINE ของผู้รับผิดชอบที่มีหนังสือ/รายการมอบหมาย หรือใช้ approval จากต้นสังกัด
- [ ] บัญชีย่อยครูที่มี `grade_scope` ต้องผูกและกู้คืนแยกจากบัญชีหลัก
- [ ] เมื่อย้ายโรงเรียน/เปลี่ยนหน้าที่ ต้อง revoke LINE และ recovery code ภายในระยะเวลาที่กำหนด

งานพัฒนา:

- [ ] เพิ่ม school ownership verification และหน้าจอส่งมอบผู้รับผิดชอบ
- [ ] รักษา `school_id` และ `grade_scope` เดิมทุกครั้งที่ reset
- [ ] แจ้ง admin/ต้นสังกัดเมื่อบัญชีหลักโรงเรียนผูก LINE, ยกเลิก หรือเปลี่ยนรหัส
- [ ] ทดสอบบัญชีหลักและบัญชีย่อย รวมถึงกรณีปิดใช้งานผู้ใช้

เกณฑ์ผ่าน: reset ไม่เปลี่ยน scope, ผู้ไม่มีอำนาจผูก LINE ไม่ได้ และมีหลักฐานการส่งมอบบัญชี

## Phase 5 - คนขับ

เป้าหมาย: รองรับ `driver` เมื่อแยกตัวตนคนขับออกจากข้อมูลรถได้ชัดเจน

ข้อขัดแย้งที่ต้องแก้ก่อน: หน้า login รองรับทะเบียนรถ แต่ LINE เป็นตัวตนบุคคล การให้คนขับคนหนึ่ง reset บัญชีที่ใช้ร่วมกับรถอาจกระทบคนขับกะอื่น

Decision gate:

- [ ] ยืนยันว่า username/ทะเบียนรถเป็นบัญชีบุคคลหรือบัญชีรถ
- [ ] หากรถมีหลายกะ ต้องใช้บัญชีคนขับแยก หรือกำหนด approval จากโรงเรียนก่อน reset
- [ ] ยืนยันวิธีจัดการเมื่อเปลี่ยนรถ เปลี่ยนกะ หรือสิ้นสุดการปฏิบัติงาน

งานพัฒนา:

- [ ] เชื่อมกับ `line_users.driver_id` โดยตรวจ unique ownership และสถานะคนขับ
- [ ] แจ้งโรงเรียนเมื่อมีการผูก/ยกเลิก LINE หรือเปลี่ยนรหัส
- [ ] ทดสอบหลายคนขับต่อรถ, เปลี่ยนกะ, บัญชีถูกระงับ และเอกสารหมดอายุ

เกณฑ์ผ่าน: คนขับไม่สามารถ reset บัญชีของรถ/คนขับอื่น และการเปลี่ยนกะไม่ทำให้บัญชีถูกยึดค้าง

## Phase 6 - ผู้ปกครองและความต่อเนื่องของ LINE

ผู้ปกครองไม่ใช่ role ใน `users` และไม่มีรหัสผ่านแบบ 6 บทบาท จึงไม่ควรนำ password recovery ไปใช้ตรง ๆ

- [ ] คงกระบวนการผูก LINE กับผู้ปกครองผ่าน `/parent/link`
- [ ] ออกแบบขั้นตอนเปลี่ยนโทรศัพท์/LINE โดยให้โรงเรียนตรวจสอบความสัมพันธ์กับนักเรียน
- [ ] ป้องกันการผูกซ้ำและยกเลิก mapping เดิมอย่างมี audit trail
- [ ] จัดทำคู่มือแยกเรื่อง “ผูกบัญชี LINE ใหม่” ไม่เรียกว่า “ลืมรหัสผ่าน”

เกณฑ์ผ่าน: ผู้ปกครองกลับมารับแจ้งเตือนได้โดยไม่มีช่องทางเข้าถึงข้อมูลเด็กอื่น

## Phase 7 - ปิดโครงการและส่งมอบงานประจำ

- [ ] อัปเดตคู่มือ PDF/เว็บไซต์แยกตามบทบาทที่เปิดจริง
- [ ] จัดทำ operator runbook, incident response และรอบตรวจ audit log
- [ ] กำหนด owner, backup owner, SLA และช่องทางช่วยเหลือ
- [ ] ทำ restore drill และ rollback drill หลังเปิดครบทุกบทบาท
- [ ] Regenerate readiness/closure bundle และขอ owner/operator/DPO sign-off ตามหน้าที่จริง

เกณฑ์เสร็จสิ้น: เปิดเฉพาะบทบาทที่มี UAT และผู้รับผิดชอบอนุมัติ, validators ไม่มี FAIL และสิ่งที่ PENDING เหลือเฉพาะ external/human action ที่ระบุชื่อผู้รับผิดชอบแล้ว

## ลำดับทำงานครั้งถัดไป

1. ทำ Phase 1 ด้วย admin จริงหนึ่งบัญชีในช่วงเวลาที่ผู้ใช้พร้อมรับ LINE
2. สรุปผล UAT และตัดสินใจเปิด Phase 2 หรือปิด flag กลับ
3. เก็บข้อมูล ownership ของจังหวัด ต้นสังกัด และขนส่ง แล้วให้เจ้าของระบบยืนยัน logic
4. พัฒนา Phase 3 หลัง decision gate เท่านั้น
5. ทำโรงเรียน คนขับ และผู้ปกครองตามลำดับ โดยแยก feature flag และ UAT ทุกกลุ่ม
