## 2. ข้อบกพร่องที่พบเองและแก้แล้ว

เรียงตามผลกระทบต่อผู้ใช้จริง ไม่ใช่ตามลำดับเวลา

### 2.1 หน้าจอบอกกฎรหัสผ่านไม่ตรงกับที่ระบบบังคับ (กระทบผู้ใช้ทุกวัน)

มีเลขขั้นต่ำสามค่าใช้อยู่พร้อมกัน เซิร์ฟเวอร์บังคับ 8 ตัวอักษรมาตลอด หน้าจัดการผู้ใช้และหน้าบัญชีครูเขียน 6
และ **หน้าโปรไฟล์คนขับเขียน 4** คนขับที่อ่านว่า "อย่างน้อย 4 ตัวอักษร" แล้วพิมพ์สี่ตัว จะถูกปฏิเสธโดยไม่มีทางรู้กฎจริง
คู่มืออบรมถึงขั้นเขียนกำกับไว้ว่าอย่าเชื่อหน้าจอ ให้จำ 8 แทน ซึ่งคือคู่มือที่ขอโทษแทนบั๊ก

แก้โดยย้ายเลขไปอยู่ที่เดียวใน `frontend/src/utils/passwordPolicy.js` และให้ทุกหน้าที่กำหนดรหัสผ่านใหม่ดึงจากที่นั่น
เทสต์เดินทุกไฟล์ในโฟลเดอร์หน้าจอ ไม่ใช่รายการที่ตายตัว จึงลืมหน้าใหม่ไม่ได้ และล้มเมื่อมีใครพิมพ์ตัวเลขลงไปเอง
ระหว่างเขียนเทสต์พบอีกหนึ่งหน้าที่ตกสำรวจ ซึ่งเป็นเหตุผลที่ต้องเดินทั้งต้นไม้

### 2.2 หน้าเปลี่ยนรหัสผ่านพัง จากการแก้ของวันนี้เอง

การแก้เรื่องรหัสผ่านเมื่อบ่ายทำให้ `ChangePassword.jsx` ใช้ชื่อ `PASSWORD_HELPER` โดยไม่ได้ import
ผลคือหน้าจอตกไปที่หน้าแจ้งข้อผิดพลาดทุกครั้งที่เปิด

**ไม่มีอะไรจับได้เลย** ชื่อที่ไม่ได้ import เป็น error ตอนรัน ไม่ใช่ตอน build คำสั่ง build จึงผ่าน
ไม่มีเทสต์ใดเปิดหน้าจอในเบราว์เซอร์ และโครงการนี้ไม่มี linter
หน้าที่พังคือหน้าที่ทุกบัญชีที่ถูกบังคับเปลี่ยนรหัสผ่านต้องผ่านตอนเข้าระบบครั้งแรก
ถ้าขึ้นระบบไปทั้งอย่างนี้ ผู้ใช้ใหม่ทุกคนจะเข้าไม่ได้ และคนแรกที่รู้จะเป็นครูที่เข้าระบบไม่ได้

พบจากการรันถ่ายภาพหน้าจอ ซึ่งเป็นสิ่งเดียวในโครงการนี้ที่เปิดหน้าจอจริง
แก้แล้ว พร้อมเพิ่มตัวดักที่ตรวจทั้งประเภทของบั๊ก ไม่ใช่เฉพาะกรณีนี้ คือทุกไฟล์ที่ import จากโมดูลกลาง
ถ้าใช้ชื่อที่โมดูลนั้นส่งออกแต่ไม่ได้ import จะมีเทสต์ล้ม ทดสอบแล้วว่าถอด import ออกทีเดียวก็แดงทันที

### 2.3 ไทม์ไลน์ของเรื่องร้องเรียนแสดงวันที่เป็นขีดทุกบรรทัด

หน้าจอรายละเอียดอ่าน `created_at` แต่ตารางเหตุการณ์ชื่อคอลัมน์ `occurred_at` และ API ก็ส่ง `occurred_at`
หน้าจอนั้นมีไว้เพื่อพิสูจน์ว่าแต่ละขั้นเกิดขึ้นเมื่อไร และมันพิสูจน์ไม่ได้เลยตั้งแต่ฟีเจอร์เปิดใช้เมื่อ 7 ก.ย.
ค่าที่ไม่มีถูกวาดเป็นขีด ไม่ใช่ error จึงไม่มีอะไรดังขึ้น บล็อกเดียวกันยังอ่าน `decision` จากเหตุการณ์ ซึ่งตารางไม่มีคอลัมน์นั้นเลย

เพิ่มเทสต์ที่เทียบสามแหล่ง คือ migration, คำสั่ง SELECT และหน้าจอ ถ้าเปลี่ยนชื่อคอลัมน์ที่ใดที่หนึ่งจะมีเทสต์ล้ม แทนที่จะมีช่องว่างเงียบ ๆ บนหน้าจอ

### 2.4 แดชบอร์ดประเมินผลประกาศแนวโน้มที่เทียบไม่ได้

ฟังก์ชันคำนวณเปอร์เซ็นต์ของหน้านี้คืน 0 เมื่อตัวหารเป็นศูนย์ ทำให้ "ยังไม่มีการเดินรถเลย" กับ "พลาดทุกเที่ยว" หน้าตาเหมือนกัน
และมันติดป้าย "ดีขึ้น" หรือ "ลดลง" โดยไม่ตรวจว่าข้อมูลคู่นั้นเทียบกันได้หรือไม่ ทั้งที่อีกสามหน้าเพิ่งถูกแก้ให้ตรวจ
สองหน้าของผู้ดูแลระบบสรุปคนละอย่างจากข้อมูลชุดเดียวกัน ซึ่งแย่กว่าผิดหน้าเดียว

### 2.5 checksum ของชุดข้อมูลวิจัยไม่ครอบคลุมข้อความที่สำคัญที่สุด

`research_claims_allowed` และก้อนหลักฐานที่มันมาจาก อยู่ใน `meta` ซึ่งถูกยกเว้นทั้งก้อน
ไฟล์ที่ดาวน์โหลดไปแล้วจึงแก้คำตอบจาก "อ้างเป็นผลวิจัยไม่ได้" เป็น "ได้" แล้วยัง verify ผ่าน
นี่คือการปลอมแปลงแบบที่ checksum มีไว้จับพอดี และเป็นทิศทางที่คนจะปลอมพอดี

### 2.6 ตัวสแกนหาความลับรายงานผลบวกลวง 18 บรรทัด

ประตูตรวจขึ้น FAIL กับ commit ที่ไม่ได้ทำข้อมูลลับรั่วเลยสักบรรทัด ทั้ง 18 รายการเป็นการอ่านค่าจาก environment
การแทนค่าจากตัวแปร คำว่า CHANGE_ME และชื่อคีย์ที่ปรากฏในข้อความแจ้งเตือน

นี่คือรูปแบบความล้มเหลวที่อันตรายที่สุดของเครื่องมือประเภทนี้ ไม่มีใครปิดเครื่องมือที่ไม่เคยเตือนผิด แต่ทุกคนจะปิดเครื่องมือที่เตือนผิดทุกสัปดาห์
แล้วครั้งที่ข้อมูลรั่วจริงจะผ่านไปเงียบ ๆ

แก้โดยแยกออกเป็นไลบรารีที่ทดสอบได้ และให้แยกแยะระหว่าง "ชื่อคีย์ปรากฏ" กับ "ค่าที่ใช้งานได้จริงปรากฏ"
เทสต์เก็บความลับจริง 13 แบบที่ต้องจับได้เสมอ ไว้คู่กับรูปแบบที่ต้องไม่เตือน และเล่นซ้ำ 18 บรรทัดจากล็อกจริงของวันนี้
พร้อมเพิ่มกฎที่ไม่เคยมี คือรหัสผ่านในสตริงเชื่อมต่อฐานข้อมูล โทเค็นรูปแบบ JWT และหัวไฟล์กุญแจส่วนตัว

### 2.7 ฮาร์เนสถ่ายภาพคู่มือกลับไปเป็นบั๊กเดิมที่มันถูกเขียนขึ้นมาแก้

ไฟล์เขียนค่าสวิตช์ฟีเจอร์ไว้ตายตัวสิบตัว และเทสต์ที่คุมมันก็เขียนค่าเดียวกันซ้ำอีกชุด
วันที่ 7 ก.ย. มีการเปิดสวิตช์จริงสองตัวโดยไม่มีใครแตะสองไฟล์นี้ เทสต์จึงยังเขียวทั้งที่ยืนยันโลกที่ไม่มีอยู่แล้ว
ถ้ารันถ่ายภาพตอนนี้จะได้คู่มือที่เป็นหน้าจอแบบปิดสวิตช์อีกรอบ ซึ่งคือข้อบกพร่องที่เพิ่งเสียภาพไป 76 ภาพเมื่อสองวันก่อน

ค่าย้ายไปอยู่ที่ `scripts/production-feature-flags.json` ที่เดียว พร้อมบันทึกว่าตรวจกับอะไรเมื่อไร
และเทสต์เลิกคัดลอกค่า เปลี่ยนไปตรวจการต่อสาย ว่าทุกสวิตช์ที่เซิร์ฟเวอร์รู้จักมีอยู่ในไฟล์ และไม่มีตัวเลขเขียนตายตัวกลับเข้ามา

### 2.8 อื่น ๆ

- ตารางสิทธิ์ล้าสมัย มีไฟล์เส้นทาง 19 ไฟล์เปลี่ยนตั้งแต่สร้าง สร้างใหม่ครบสามชุดสวิตช์ ไม่พบข้อบกพร่องและไม่พบช่องโหว่ขอบเขต
- คำอธิบายขนาด connection pool อ้างตัวเลขที่เอกสารต้นทางไม่ได้เขียนไว้ แก้ให้ตรงกับที่วัดได้จริง
- เทสต์ที่คุมความถูกต้องงานวิจัยเฝ้าชื่อฟิลด์ที่ถูกเปลี่ยนไปแล้ว จึงเฝ้าคำที่ไม่มีใครใช้ เปลี่ยนไปยืนยันคุณสมบัติแทนชื่อ
- ตัวตรวจการเขียนทับบันทึกเหตุการณ์มีช่องโหว่เรื่องเครื่องหมายอ้างชื่อตาราง เขียนแบบผสมสองรูปแบบแล้วรอดไปได้ ปิดแล้วพร้อมเพิ่มสามรูปแบบเป็นกรณีทดสอบ
- ไฟล์ `.docx` ของราชการที่ลงนามแล้ว ขนาด 38 MB วางอยู่ในรากของ repo โดยไม่มีอะไรกันไว้ ตอนนี้ commit ไม่ได้แล้ว

## 3. เรื่องที่พบบนเว็บจริง

สร้างเครื่องมือ `scripts/check-live-pages.mjs` ที่เปิดหน้าสาธารณะเจ็ดหน้าด้วยเบราว์เซอร์จริงและฟัง error แบบที่ผู้ใช้เจอ
ประตูตรวจเดิมดูแค่ว่าเซิร์ฟเวอร์ตอบ 200 ซึ่งผ่านได้แม้หน้าจะพัง เพราะแอปเป็นหน้าเดียวที่ทุกอย่างเกิดในเบราว์เซอร์

**ผลการรันครั้งแรกพบของจริง** Cloudflare แทรกสคริปต์เก็บสถิติเข้าทุกหน้า แล้วถูกนโยบายความปลอดภัยของเราบล็อก
ยังไม่มีข้อมูลรั่วเพราะบล็อกได้จริง บันทึกเป็น RR-11 พร้อมเตือนไว้ชัดว่า **ห้ามแก้ด้วยการขยายนโยบาย**
เพราะจะกลายเป็นการส่งข้อมูลการเปิดหน้าที่เกี่ยวกับเด็กออกไปให้ผู้ประมวลผลภายนอกที่หน่วยงานไม่มีข้อตกลงด้วย
ทางแก้ที่ถูกคือปิด Browser Insights ในแดชบอร์ดของ Cloudflare

| ผู้ดูแลระบบ · โรงเรียน · สังกัด · ขนส่ง · คนขับ (เว็บ) | เพิ่มหัวข้อเดียวกันในคู่มือฉบับที่เผยแพร่บนเว็บ |
| ทุกฉบับที่พูดถึงรหัสผ่าน | เลิกเขียนกำกับว่าอย่าเชื่อหน้าจอ เพราะหน้าจอถูกแล้ว |
| ภาพประกอบ | เพิ่มภาพหน้าจอของกล่องรับเรื่อง 16 ภาพ ครอบคลุมห้าบทบาท จากเดิมที่ไม่มีเลยสักภาพ และถ่ายภาพเดิมใหม่ 67 ภาพ เพราะชุดเดิมถ่ายตอนที่ยังปิดสวิตช์ เมนูสองรายการที่คู่มือบอกว่าอยู่บนสุดจึงไม่ปรากฏในภาพ |

**ข้อความที่ต้องแก้เพราะไม่ตรงกับโค้ด** คู่มือเจ็ดฉบับเขียนตรงกันว่าระบบบังคับลำดับขั้น ข้ามไม่ได้
ความจริงระบบบังคับข้อเดียว คือแจ้งผลกลับผู้เสนอทำได้ต่อเมื่อสถานะเป็นดำเนินการเสร็จแล้วเท่านั้น
นอกนั้นข้ามขั้นได้ เรื่องหนึ่งจึงปิดได้โดยไม่เคยผ่านขั้นรับเรื่องเลย แก้ทั้งเจ็ดฉบับให้ตรงกัน
พร้อมแก้อีกสามข้อ คือชื่อตัวกรองบนหน้าจอ ใครถอนเรื่องได้บ้าง และการระบุผู้รับเรื่องซึ่งเป็นข้อตกลงของหน่วยงาน ไม่ใช่สิ่งที่โปรแกรมบังคับ

| เรื่อง | เหตุผล |
|---|---|
| **ยังไม่ deploy** | คำสั่ง ssh ของผู้ช่วยถูกตัวกรองบล็อก แม้เป็นการอ่านอย่างเดียว การ deploy จึงต้องให้ผู้ดูแลระบบรันเอง — ดู §7 |
| เปิดสวิตช์กู้รหัสผ่านให้อีก 3 บทบาท | รอคำตอบสามข้อต่อบทบาทจากเจ้าของโครงการและผู้รับผิดชอบข้อมูลส่วนบุคคล |
| ตรวจว่าใครมีสิทธิ์บันทึกมติ | รอคำตอบ C0-2 ปัจจุบันผู้ที่เห็นเรื่องบันทึกมติในเรื่องของตัวเองได้ มีเทสต์บันทึกพฤติกรรมนี้ไว้แล้วพร้อมคำอธิบายว่าเป็นข้อบกพร่องที่รอการตัดสิน |
| ช่องทางให้ผู้ปกครองยื่นเรื่อง | แผนระบุเองว่าต้องรอขอบเขตที่เจ้าของและ DPO อนุมัติ |
| รายงานผลรองรับผู้ใช้ 1,000 คน | ต้องใช้เครื่องแยกที่ยังไม่มี |

## 7. ถ้าจะขึ้นระบบจริง

การเปลี่ยนแปลงของวันนี้ **ไม่มี migration ไม่มีการเปลี่ยนสวิตช์ และไม่แตะฐานข้อมูล** จึงเป็นการ deploy แบบธรรมดา
ลำดับตามที่ใช้มาทุกครั้ง คือสำรองฐานข้อมูลและตรวจสอบไฟล์สำรองก่อน แล้วรัน `scripts/deploy-backend.sh`
ตามด้วย build หน้าเว็บใหม่ แล้วเฝ้าดู 15 นาที รายละเอียดของแต่ละขั้นอยู่ใน `docs/ops/deploy-2026-09-07-f60aee5.md` §7

**สิ่งที่ผู้ใช้จะเห็นต่างจากเดิมทันที** ข้อความความยาวรหัสผ่านถูกต้องทุกหน้า · ไทม์ไลน์ของเรื่องร้องเรียนมีวันที่ ·
หน้าสรุปภาพรวมการมีส่วนร่วมที่ยังไม่เคยมีใครเห็น · และหน้ารายงานวิจัยเลิกประกาศแนวโน้มที่ยังเทียบกันไม่ได้
