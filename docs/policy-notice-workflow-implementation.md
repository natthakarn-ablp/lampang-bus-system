# Role-based policy notice candidate

Status: **draft review mode approved by the product owner; legal approval remains pending**. The draft may be displayed on production so legal and operational stakeholders can inspect the real responsive flow. Every surface labels it as a meeting draft. Review mode does not approve a legal basis, write acknowledgement/action evidence, grant consent, block work, or change existing access rights.

The staff routes cover school, driver, transport, affiliation, province, and admin. Each receives the common topic and one role topic. The server determines the role from the authenticated token and rejects a different topic or an obsolete version. Acknowledgements have their own append-only table (`052_policy_acknowledgements.sql`) and a required audit entry. They are separate from QR/LINE `consent_records`; pressing “รับทราบ” must never be interpreted as consent. The modal offers “อ่านภายหลัง” and is suppressed on emergency paths. While `APPROVED` remains false, the server returns `reviewMode:true` with labelled draft text and refuses every acknowledgement/evidence write. The browser stores only a local “draft seen” marker.

The candidate implements per-action evidence for applying a student-import batch, starting a driver shift, recording a vehicle inspection, exporting staff reports, exporting the transport vehicle-safety CSV, and exporting the admin research package. The browser asks the server for the exact role/context text. In review mode it displays the real dialog and continues under existing RBAC without issuing evidence. If an approved policy is activated later, the server records a minimized claim and returns a random token that expires after ten minutes. The protected action consumes that token once and checks actor, role, context, subject type, subject id, date/range/format where applicable, topic and version. `053_policy_action_evidence.sql` stores certification/warning evidence separately from both acknowledgement and consent. Claims are server-whitelisted; names, phone numbers, free-text notes and uploaded rows are never accepted into this ledger.

All staff roles receive a permanent `นโยบายและสิทธิของฉัน` route. In review mode it shows only the labelled meeting draft; after legal activation it shows the approved version. It explains whether a topic appears at first use, before certification, or before export. The implementation deliberately does not add a popup to every attendance tap or cover emergency controls.

Before a responsible controller can approve and activate a version, record and review for each activity:

1. The actual controller, DPO/contact channel, data categories and source, purpose and lawful basis, recipients, retention/deletion rule, rights channel, and any international transfer.
2. The full Thai text and its accessible permanent URL. The role summary in `policyNotices.js` is a draft and is insufficient alone. Version and hash must cover the exact complete text shown.
3. Which actions need a notice, which need a separate certification, and which (if any) truly require consent. School staff cannot consent on behalf of a child or parent.
4. A safe migration/rollback, six-role browser and API UAT, keyboard/mobile tests, and human review of the actual text. Parent LIFF and QR remain separate and cannot be signed off without a separate test environment.

The decision register template is `docs/policy-notice-decision-register.md`. Its controller, approver and public contact fields remain `UNDECIDED` because the owner confirmed they have not yet been designated. That is an activation blocker, not a value the development team may infer.

Legal activation must be a separate reviewed change after those decisions. `APPROVED` is computed from the review fields, a full-notice URL, body text, lawful basis and retention rule for every topic; review mode cannot satisfy it. The ledger stores the exact approved notice snapshot and its hash. Deploying the labelled review UI does not make it a legal notice and must not enable QR/LINE flags.
