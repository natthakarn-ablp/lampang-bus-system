# Decision Package: การเปิดระบบกู้คืนบัญชีรายบทบาท

ระบบ: อุ่นใจไปโรงเรียน (School Safe Connect)

จัดทำ: 4 กันยายน 2569

สถานะเอกสาร: **ชุดข้อมูลเพื่อให้ผู้มีอำนาจตัดสินใจ ไม่ใช่การอนุมัติ และไม่ใช่ผลการทดสอบ**

เอกสารอ้างอิง: `docs/password-recovery-all-roles-roadmap.md`

---

## 1. เรื่องที่ต้องตัดสินใจ

`docs/password-recovery-all-roles-roadmap.md` กำหนดให้การกู้คืนบัญชีครบทุกสิทธิ์เป็นขอบเขตบังคับก่อนปิดโครงการ แต่ห้ามเดา business logic ของแต่ละบทบาท

กลไกทางเทคนิคสร้างเสร็จแล้วและใช้ร่วมกันได้ทุกบทบาท สิ่งที่ยังขาดคือ **การตัดสินใจว่าบัญชีของแต่ละหน่วยงานเป็นบัญชีบุคคลหรือบัญชีกลาง และใครมีอำนาจผูก LINE** ซึ่งเป็นอำนาจของเจ้าของระบบ ไม่ใช่ของทีมพัฒนา

## 2. สิ่งที่ระบบทำไว้แล้ว (ไม่ต้องตัดสินใจ)

| รายการ | สถานะ |
|---|---|
| Migration `049_admin_password_recovery.sql` (additive) | apply บน production แล้ว |
| Token/recovery code เก็บแบบ hash ไม่มี plaintext | ทำแล้ว |
| ลิงก์อายุ 15 นาที ใช้ครั้งเดียว ล็อกเมื่อผิด 5 ครั้ง | ทำแล้ว |
| ตรวจ LIFF ID Token ฝั่ง server และทดสอบ push ก่อนบันทึกการผูก | ทำแล้ว |
| เปลี่ยนรหัสแล้ว session เดิมหมดอายุผ่าน `password_changed_at` | ทำแล้ว |
| Audit event ครบทุกขั้นตอน | ทำแล้ว |
| Endpoint self-service แยกจาก policy รายบทบาท (`/api/auth/recovery/self/*`) | ทำแล้ว (commit นี้) |
| Role allowlist + feature flag แยกกลุ่ม ค่าเริ่มต้นปิดทุกบทบาท | ทำแล้ว (commit นี้) |
| Decision gate บังคับก่อนเปิดบทบาท | ทำแล้ว (commit นี้) |

การเปลี่ยนรหัสผ่านไม่แตะคอลัมน์ `role`, `scope_type`, `scope_id`, `grade_scope`, `driver_id`, `is_active` — มี test บังคับไว้ ดังนั้นการ reset จะไม่ทำให้ขอบเขตของครูหรือโรงเรียนเปลี่ยน

## 3. กลไกป้องกันการเปิดโดยไม่ตั้งใจ

บทบาทจะเปิดได้ต่อเมื่อ **ครบทั้งสองเงื่อนไข**:

1. `gatesConfirmed: true` ใน `backend/src/config/accountRecoveryPolicy.js` — แก้ได้เฉพาะการแก้ไฟล์และ commit ซึ่งจะปรากฏใน diff คู่กับเอกสารอนุมัติ
2. Feature flag ของบทบาทนั้นถูกตั้งเป็น `true` บน server

การตั้ง environment variable เพียงอย่างเดียว **เปิดบทบาทไม่ได้** ต่อให้ตั้งครบทุกตัว ระบบยังเปิดเฉพาะ `admin` เท่านั้น

### 4.5 คนขับ (driver) — มีข้อขัดแย้งที่ต้องแก้ก่อน

หน้า login ของคนขับใช้ทะเบียนรถ แต่บัญชี LINE เป็นตัวตนของบุคคล ถ้ารถหนึ่งคันมีคนขับหลายกะและใช้ username เดียวกัน การที่คนขับคนหนึ่ง reset รหัสผ่านจะทำให้คนขับกะอื่นเข้าระบบไม่ได้ทันที

| Gate | คำถาม | คำตอบ | ผู้ตัดสิน | วันที่ |
|---|---|---|---|---|
| `driver_username_is_person_or_vehicle` | username/ทะเบียนรถเป็นบัญชีบุคคลหรือบัญชีรถ | ☐ บุคคล ☐ รถ | | |
| `multi_shift_vehicle_requires_separate_accounts_or_school_approval` | ถ้าเป็นบัญชีรถและมีหลายกะ จะแยกบัญชีรายบุคคล หรือให้โรงเรียนอนุมัติก่อน reset | ☐ แยกบัญชี ☐ โรงเรียนอนุมัติ | | |
| `driver_change_of_vehicle_or_shift_handling` | เมื่อเปลี่ยนรถ เปลี่ยนกะ หรือสิ้นสุดการปฏิบัติงาน ต้องทำอย่างไรกับการผูก LINE | | | |

### 4.6 ผู้ปกครอง (parent) — ไม่ใช่การลืมรหัสผ่าน

ผู้ปกครองไม่มีรหัสผ่านในระบบ กระบวนการคือการยกเลิกและผูก LINE ใหม่ ห้ามเรียกว่า "ลืมรหัสผ่าน" ในคู่มือหรือ UI

| Gate | คำถาม | คำตอบ | ผู้ตัดสิน | วันที่ |
|---|---|---|---|---|
| `parent_rebind_verification_owner` | ใครตรวจสอบความสัมพันธ์กับนักเรียนก่อนผูก LINE ใหม่ | ☐ โรงเรียน ☐ ต้นสังกัด ☐ อื่น ______ | | |
| `parent_duplicate_binding_prevention` | ถ้าเบอร์/LINE เดิมยังผูกอยู่ ต้องยกเลิกอัตโนมัติหรือให้เจ้าหน้าที่ยืนยัน | ☐ อัตโนมัติ ☐ เจ้าหน้าที่ยืนยัน | | |
| `parent_unbind_audit_requirements` | ต้องเก็บหลักฐานอะไรบ้างเมื่อยกเลิก mapping เดิม | | | |

## 5. ขั้นตอนหลังได้คำตอบ

1. บันทึกคำตอบและลายเซ็นในเอกสารนี้
2. ทีมพัฒนาแก้ `gatesConfirmed` ของบทบาทนั้นเป็น `true` พร้อมอ้างอิงเอกสารนี้ใน commit message
3. เพิ่ม/ปรับ test ของ RBAC, scope, enumeration resistance, concurrent reset และ audit log ตามรูปแบบที่ตัดสินใจ
4. เปิด feature flag ของบทบาทนั้นบน server
5. ทำ UAT กับผู้ใช้จริงอย่างน้อยหนึ่งบัญชีต่อบทบาท และเก็บหลักฐานแบบ redacted
6. ผู้รับผิดชอบหน่วยงานลงนามรับรองก่อนถือว่าบทบาทนั้นผ่าน

## 6. สิ่งที่เอกสารนี้ไม่ได้ทำ

- ไม่ได้อนุมัติการเปิดบทบาทใด
- ไม่ได้แทนการทำ UAT หรือลายเซ็นของผู้มีอำนาจ
- ไม่ได้ยืนยันว่า Admin ผ่าน Phase 1 แล้ว — Admin ยัง deploy แบบ dark launch และรอ UAT กับ admin จริง
