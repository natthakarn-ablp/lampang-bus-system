## ขั้นตอนปล่อยที่ผู้ดูแลดำเนินการภายหลัง

1. ให้เจ้าของ review และ merge PR ตามลำดับนี้เข้า `feat/tracking-security-hardening` หลัง required checks ของแต่ละ PR ผ่าน: **#46 → #50 → #53 → #51 → #52 → #54**
2. ก่อนเริ่ม deploy ให้ทำ preflight และสำรองฐานข้อมูลตามรูปแบบใน [`docs/ops/deploy-2026-10-02-205310a.md`](../ops/deploy-2026-10-02-205310a.md) โดยตรวจยืนยันไฟล์ backup ว่า verify ผ่านก่อนดำเนินการต่อ และบันทึกหลักฐานจริงใน deploy record:

   | รายการ preflight | ค่าที่ต้องบันทึก |
   |---|---|
   | ชื่อไฟล์ DB backup | `[ผู้ดูแลบันทึกชื่อไฟล์จริงก่อน deploy]` |
   | ผล verify | `PASS` เท่านั้นจึงดำเนินการต่อ พร้อมบันทึกวิธีตรวจและเวลา |

   ห้ามเริ่ม deploy หากไม่มีไฟล์ backup หรือผล verify ไม่ผ่าน; เอกสารนี้ไม่ได้สร้างหรือยืนยัน backup สำหรับรอบ deploy ในอนาคต
3. บน checkout production ให้ `git fetch origin` แล้วสลับไป branch `feat/tracking-security-hardening` ด้วย `git switch feat/tracking-security-hardening` (ห้ามใช้ detached HEAD); ตรวจ working tree ให้สะอาดและยืนยันว่า remote branch ตรงกับ SHA เป้าหมายที่เจ้าของอนุมัติ:

   ```bash
   git fetch origin
   test "$(git rev-parse origin/feat/tracking-security-hardening)" = "$TARGET_SHA"
   ```

   ถ้าไม่ตรงให้หยุดและให้เจ้าของอนุมัติ SHA ใหม่; ห้าม push เพิ่มระหว่าง deploy
4. จาก root ของ checkout ให้รัน `EXPECTED_BRANCH=feat/tracking-security-hardening bash scripts/deploy-backend.sh` สคริปต์จะ fetch branch และ fast-forward เท่านั้น จากนั้นจัดการ deploy lock, syntax check, unit tests, PM2 reload, health check และ auto-rollback ตามผลตรวจของสคริปต์ ห้ามแทนที่ flow นี้ด้วย `git checkout --detach` หรือ `git pull` เอง สคริปต์บันทึก backend rollback ref (`rollback_ref`) ใน deploy history; ถ้า health หลัง reload ไม่ผ่าน สคริปต์จะ rollback ตาม ref นั้นและบันทึกผล
5. หลัง backend ผ่านแล้ว ก่อน build frontend ให้สำรอง `frontend/dist` ไว้ข้างเดิมด้วย timestamp UTC และห้ามเขียนทับ backup ที่มีอยู่:

   ```bash
   cd frontend
   STAMP="$(date -u +%Y%m%d-%H%M)"
   test -d dist
   test ! -e "dist.prev-$STAMP"
   cp -a dist "dist.prev-$STAMP"
   npm ci
   npm run build
   ```

   หากต้อง rollback frontend ให้ย้าย build ปัจจุบันออกก่อน (ถ้ามี) แล้วคืน backup ด้วยการย้ายไฟล์; ใช้ timestamp ที่บันทึกไว้ใน deploy record:

   ```bash
   test -d "dist.prev-$STAMP"
   if [ -e dist ]; then mv dist "dist.failed-$STAMP"; fi
   mv "dist.prev-$STAMP" dist
   ```

   เก็บชื่อ `dist.prev-$STAMP` ไว้ใน deploy record จนยืนยันผลหลัง deploy ครบ
6. เช็คลิสต์หลังปล่อย:
   - `GET /api/health` ตอบ HTTP 200 และค่า `commit` ตรงกับ 7 ตัวแรกของ `<TARGET_SHA>`
   - ชื่อ `index-*.js` ใน HTML ที่เว็บส่งจริงตรงกับไฟล์ที่ build จาก SHA นี้
   - บัญชีครูสายชั้นสำหรับ UAT เรียก `/api/documents/...` แล้วได้ HTTP 403 และรหัส `FULL_SCHOOL_SCOPE_REQUIRED`
   - ใช้บัญชี UAT ส่งออกรายงานหนึ่งไฟล์ และตรวจว่ามีแถว action `EXPORT` ใน `audit_logs`; ห้ามบันทึกหรือแนบข้อมูลรายงาน/ข้อมูลบุคคลใน deploy record
   - ทดสอบล็อกอินครบทุก role ด้วยบัญชี UAT ที่ได้รับอนุญาต
   - `pm2 logs schoolbus-backend` ไม่มี error ใหม่ที่สัมพันธ์กับ release
7. บันทึกเวลา, ผู้ปฏิบัติงาน, `<TARGET_SHA>`, ผล health/assets/access/login/log checks, ชื่อ DB backup พร้อมผล verify, ชื่อ frontend backup, และ `rollback_ref` จาก deploy history; ช่องที่ไม่มีหลักฐานให้ระบุ NOT VERIFIED

**สถานะการดำเนินงาน:** ขั้นตอนข้อ 1–4 ข้างต้นยังไม่ได้ดำเนินการสำหรับ release รอบนี้: ยังไม่มีการ merge PR ตามข้อ 1, ไม่มีการสำรองและ verify ฐานข้อมูลตามข้อ 2, ไม่มีการ checkout/fast-forward หรือรัน `scripts/deploy-backend.sh` ตามข้อ 3–4, และไม่มีการ build หรือเผยแพร่ frontend ตามข้อ 5. ห้ามข้าม required checks หรือใช้ detached HEAD; ห้าม deploy ก่อนเจ้าของ merge และอนุมัติ SHA เป้าหมาย, ห้ามรัน migrations 052/053, และห้ามใช้คำสั่ง deploy อื่นแทนสคริปต์ที่กำหนด

## ข้อมูลที่ขอจากผู้ดูแลเครื่อง

- **S07 proxy:** ส่งเฉพาะ block `server` และ `location /api/` ที่เกี่ยวข้อง โดยคัดมาเฉพาะบรรทัด `set_real_ip_from`, `real_ip_header`, และ `proxy_set_header X-Forwarded-For`; ยืนยันด้วยคำตอบว่า backend รับ connection เฉพาะจาก `127.0.0.1` หรือไม่; แจ้งเพียงจำนวน IP ไม่ซ้ำใน `audit_logs` ช่วง 7 วันล่าสุด ห้ามส่ง IP จริง, token, หรือข้อมูลบุคคล
- **S10 headers:** อ้างอิง [`docs/ops/security-headers-proposal.md`](../ops/security-headers-proposal.md) และเริ่มทดสอบด้วย `Content-Security-Policy-Report-Only`; ส่งกลับเฉพาะรายการ directive/origin ที่ถูกรายงาน โดยลบ IP, query string, token, และข้อมูลส่วนบุคคลก่อน

## Prohibitions and release state

ห้าม merge โดย agent, deploy/reload, SSH, เปลี่ยน nginx/Cloudflare, หรือเขียน production DB ในขั้นตอนเตรียมเอกสารนี้; ผู้ดูแลเป็นผู้ดำเนินการเมื่อได้รับอนุมัติแยกต่างหากเท่านั้น. `TARGET_SHA` ยังคง **NOT FINALIZED** จนกว่าจะ merge PR ทั้งหมดตามลำดับและอนุมัติ SHA เต็มหลังตรวจ required checks. ขั้นตอนข้อ 1–4, การสำรอง/verify ฐานข้อมูล, การ build/publish frontend และ post-deploy checks **ยังไม่ได้ดำเนินการ**.

## Rollback

Backend: ใช้ `rollback_ref` ที่ `scripts/deploy-backend.sh` บันทึกไว้ใน deploy history ของรอบนั้น; เมื่อ health check หลัง reload ล้มเหลว สคริปต์จะคืน backend ไปยัง ref ดังกล่าวเอง หากต้องกู้คืนด้วยมือ ให้ใช้ SHA เต็มจาก `rollback_ref` และขั้นตอนที่สคริปต์พิมพ์ไว้ ห้ามชี้ branch deploy ย้อนหลังหรือใช้ detached HEAD

Frontend: คืนไฟล์ที่สำรองไว้ด้วยการย้าย `dist.prev-$STAMP` กลับเป็น `dist` ตามคำสั่งข้างต้น และบันทึก timestamp ที่ใช้

ตามบริบท release นี้ rollback เป้าหมายคือ `658f908` (`658f90862292455e5cb291acb290e0aa8223bf0d`); ให้ตรวจค่า `rollback_ref` ใน deploy history ว่าตรงกับ SHA เต็มนี้ก่อน หากไม่ตรง ห้ามเดาหรือแก้ branch บน remote เพื่อย้อน history ให้หยุดและให้ผู้ดูแลกำหนดขั้นตอนกู้คืนตามหลักฐานจริง ใช้ rollback ref/คำสั่งที่ `scripts/deploy-backend.sh` บันทึกหรือพิมพ์ไว้ แล้วตรวจ health/assets/login/logs ซ้ำ

ไม่มี migration ใหม่ใน release range นี้ จึงไม่มี migration rollback ใหม่ที่ต้องรัน ห้ามสั่งรันหรือ drop ตาราง 052/053 ระหว่าง deploy/rollback
