# รายงานตรวจเมนู การใช้งาน และความพร้อมสำหรับงานวิจัยการบริหารแบบมีส่วนร่วม

ชื่อระบบ: อุ่นใจไปโรงเรียน (School Safe Connect)

วันที่ตรวจ: 4 กันยายน 2569

สถานะเอกสาร: ผลวิเคราะห์เพื่อให้เจ้าของระบบยืนยัน Logic ก่อนปรับ UI/ฐานข้อมูล ไม่ใช่ UAT sign-off และไม่ใช่ผลการวิจัย

## 1. ขอบเขตและวิธีตรวจ

ตรวจจาก:

- Frontend routes, Sidebar, dashboard และหน้าวิจัยของทุกบทบาท
- Backend API, RBAC, audit log, report, snapshot และ decision-log implementation
- ภาพหน้าจอคู่มือของ Admin, School และหน้าประเมินผล
- Production แบบ read-only: commit, feature flags และ audit aggregates 90 วัน โดยไม่อ่าน/แก้ข้อมูลส่วนบุคคล
- Backend unit tests, frontend production build และ UI label validator

ข้อจำกัด:

- ไม่มี page-view telemetry รายเมนู จึงบอกไม่ได้อย่างมีหลักฐานว่าผู้ใช้กดหน้าใดบ่อยที่สุด
- รอบนี้ไม่สร้างบัญชีทดสอบและไม่ทำ write UAT บน production
- คำว่า "ใช้งานได้" ในรายงานหมายถึงมี route/API/guard และ build/test ผ่าน ไม่เท่ากับผู้ใช้ทุกบทบาททำ UAT ผ่านแล้ว

## 4. ความเหมาะสมรายบทบาทและข้อเสนอปรับเมนู

ตัวเลขเมนูเป็นรายการที่เห็นเมื่อใช้ feature flags ของ production ปัจจุบัน

### 4.1 Driver: ปัจจุบันประมาณ 6 รายการ แนะนำ 5 รายการหลัก

| กลุ่มปัจจุบัน | คำตัดสิน |
|---|---|
| ภาพรวม/เช็กชื่อประจำวัน | ต้องเก็บ เป็นงานหลักและเหมาะกับมือถือ |
| รายชื่อเด็กในรถ | ต้องเก็บ เพราะเป็น workflow ใหม่ที่เปิดใช้แล้ว |
| สถานะส่งตรวจรถ | ควรรวมเป็น tab ใน "รายชื่อเด็กในรถ/การลงทะเบียน" |
| แผนที่จุดรับส่ง | ต้องเก็บ ใช้ระหว่างปฏิบัติงาน |
| เหตุฉุกเฉิน | ต้องเก็บและให้เข้าถึงเร็ว |
| ข้อมูลคนขับ | ต้องเก็บเป็นเมนูบัญชี/โปรไฟล์ ไม่จำเป็นต้องอยู่กลาง workflow |

ระบบซ่อน "คำขอรายชื่อ" รุ่นเก่าเมื่อเปิด Driver Registration แล้ว ถือว่า deduplicate ถูกทาง เมนูที่เหลือไม่มากเกินไป

### 4.2 School full: ปัจจุบัน 13 รายการ แนะนำ 8 กลุ่มหลัก

| กลุ่มปัจจุบัน | คำตัดสิน |
|---|---|
| ภาพรวมโรงเรียน/ยืนยันแทนคนขับ | ต้องเก็บ เป็นงาน Phase 1 |
| ข้อมูลนักเรียน | ต้องเก็บ รวม import/history/transfer เป็น action ภายในหน้าเดียว |
| รถรับส่ง + เพิ่มรถรับส่ง | ซ้ำทางโครงสร้าง ควรรวม "เพิ่มรถ" เป็นปุ่มในหน้ารถ |
| คำขอรายชื่อ + ตรวจลงทะเบียนรถ | workflow เก่า/ใหม่ทับกัน ควรรวมเป็น "คำขอและลงทะเบียนรถ" พร้อม tabs หรือซ่อน legacy เมื่อไม่มีงานค้าง |
| ส่งตรวจและรับรองรถ | มีหน้าที่ต่างจากลงทะเบียน แต่เป็นขั้นถัดกัน ควรอยู่ในกลุ่ม "งานรถ" เดียวกัน |
| บัญชีครูประจำสายชั้น | ต้องเก็บ แต่ย้ายไป "ตั้งค่าโรงเรียน" |
| แผนที่จุดรับส่ง + ตำแหน่งปัจจุบัน | ข้อมูลคนละชนิดแต่ใช้บริบทเดียวกัน ควรรวมเมนู "แผนที่" แล้วแยก 2 tabs |
| เหตุฉุกเฉิน | ต้องเก็บ |
| ประวัติการแก้ไข | ต้องเก็บในหมวดตรวจสอบ ไม่ใช่งานประจำวัน |
| รายงาน | ต้องเก็บเป็นทางเข้าเดียว ปัจจุบันใช้ tabs ภายในเหมาะสมแล้ว |

บัญชีครูแบบ grade scope เห็นข้อมูลเฉพาะชั้นและหน้าบางส่วนแบบ read-only ซึ่งเหมาะกับหลัก least privilege แต่ต้องยืนยันกับเจ้าของงานว่าใน Phase 1 ครูประจำชั้นควร "เช็กเด็ก" ได้หรือไม่ เพราะ backend ปัจจุบันสงวน check-in override ให้บัญชีโรงเรียนเต็มเท่านั้น

### 4.3 Affiliation: ปัจจุบัน 12 รายการ แนะนำ 7 กลุ่มหลัก

| กลุ่มปัจจุบัน | คำตัดสิน |
|---|---|
| ภาพรวม | ต้องเก็บ เน้นโรงเรียนที่ยังไม่ครบ/ความเสี่ยง/สิ่งที่ต้องติดตาม |
| โรงเรียนในสังกัด + เพิ่มโรงเรียนใหม่ | ซ้ำกัน ควรรวม "โรงเรียนและบัญชี" |
| ข้อมูลนักเรียน + รถรับส่ง | เก็บเป็น drill-down จากโรงเรียน ไม่จำเป็นต้องเด่นเท่างานติดตาม |
| คำขอโอนย้าย + คำขอรถ | ต้องเก็บ แต่รวมเป็น "งานรอพิจารณา" พร้อม tabs |
| ตำแหน่งปัจจุบัน + แผนที่จุดรับส่ง | รวมเป็น "แผนที่และความเสี่ยง" |
| เหตุฉุกเฉิน | ต้องเก็บ |
| ประวัติการแก้ไข | ต้องเก็บในหมวดกำกับดูแล |
| รายงาน | ต้องเก็บ |

หน้าที่ของสังกัดควรเปลี่ยนน้ำหนักจาก "เปิดดูข้อมูล" ไปเป็น "รับทราบ-ติดตาม-ปิดเรื่อง" เพื่อสร้างหลักฐานการบริหารแบบมีส่วนร่วม

### 4.4 Province: ปัจจุบัน 11 รายการ แนะนำ 6 กลุ่มหลัก

| กลุ่มปัจจุบัน | คำตัดสิน |
|---|---|
| ภาพรวมจังหวัด | ต้องเก็บ |
| สังกัด + โรงเรียน + นักเรียน + รถ | ควรรวมเป็น "เครือข่ายและข้อมูลจังหวัด" แล้ว drill-down |
| ตำแหน่งปัจจุบัน + จุดรับส่ง | รวมเป็น "แผนที่จังหวัด" |
| เหตุฉุกเฉิน/ความเสี่ยง | ต้องเก็บและเพิ่มการรับทราบ/มอบหมาย/ติดตาม |
| ความพร้อมเปิดใช้งาน | เหมาะกับ Project owner/Operator มากกว่างานประจำของจังหวัด ควรย้ายเป็นหน้า secondary หรือรายงานช่วง rollout |
| ประวัติการแก้ไข | ต้องเก็บ |
| รายงาน | ต้องเก็บ โดย Policy report เฉพาะ Province/Admin ถูกต้องแล้ว |

Province มี decision-log ก่อน export PDF แต่เป็น optional, ไม่มี validation และ production ยังไม่มี decision-log แม้แต่รายการเดียว จึงยังใช้พิสูจน์การตัดสินใจเชิงนโยบายไม่ได้

### 4.5 Transport: ปัจจุบัน 4 รายการ แนะนำ 3-4 กลุ่ม

| กลุ่มปัจจุบัน | คำตัดสิน |
|---|---|
| ภาพรวมตรวจสภาพ | ต้องเก็บ |
| ตรวจรับรองรถ + บันทึกตรวจสภาพ | เป็นคนละขั้นของงานเดียว ควรรวมเป็น "คิวงานตรวจรถ" พร้อม tabs |
| รายการรถ | route มีอยู่แต่ไม่แสดงใน Sidebar ใช้เป็น drill-down จากคิวได้ ไม่ต้องเพิ่มเมนู |
| แผนที่จุดรับส่ง | เก็บได้ในฐานะข้อมูลรวมและไม่มี PII แต่เป็นงานรอง |

เมนูไม่มากเกินไป ปัญหาคือควรทำสถานะ OPEN-IN PROGRESS-CLOSED และ SLA ให้ครบ เพื่อวัดการปิดความเสี่ยงจริง

### 4.6 Admin: ปัจจุบันประมาณ 23 รายการ แนะนำ 8 กลุ่มหลัก

Admin เป็นบทบาทที่รกที่สุด และสลับไปหน้า School, Province, Affiliation และ Transport โดยตรง ทำให้เกิด mental context switching

ควรเหลือทางเข้าหลัก:

1. ศูนย์ควบคุมระบบ
2. ผู้ใช้และหน่วยงาน
3. คำขอและการอนุมัติ
4. คุณภาพข้อมูลและความปลอดภัยรถ
5. ปฏิบัติการระบบ: health, readiness, audit
6. วิจัยและประเมินผล
7. รายงานและส่งออก
8. ตั้งค่าระบบ

หน้า "กรอบวัดผล", "เปรียบเทียบ Baseline", "ส่งออกข้อมูลวิจัย", "ประเมินผลแยก Role" และ "สรุปผู้บริหาร" ไม่ควรเป็น 5 เมนูระดับเดียวกัน ให้รวมเป็น module เดียวที่มี 3 tabs:

- ภาพรวมผลและ Baseline
- การมีส่วนร่วมและหลักฐานแยกบทบาท
- ชุดข้อมูล/ส่งออก/กรอบวิธีวัด

### 4.7 Parent: ปัจจุบัน 2 เส้นทางหลัก

- ผูกบัญชี LINE
- ดูสถานะ/ประวัติบุตรหลาน

จำนวนไม่มากเกินไป แต่ยังขาดหน้าจัดการความเป็นส่วนตัว ถอน consent, unlink/rebind และช่องทางส่งข้อเสนอ/feedback จึงยังเป็นผู้รับข้อมูลมากกว่าผู้มีส่วนร่วม

## 6. ความครอบคลุมสำหรับงานวิจัยการบริหารแบบมีส่วนร่วม

### 6.1 สิ่งที่ระบบวัดได้ดีแล้ว

- การนำข้อมูลเข้าสู่ระบบ ความครบถ้วน ความถูกต้อง และความทันเวลา
- การปฏิบัติการ check-in/out, pretrip, ตรวจรถ, คำขอ และการอนุมัติ
- ความรับผิดชอบย้อนหลังผ่าน audit logs
- ผลลัพธ์เชิงบริการบางส่วน เช่น completion, vehicle safety, emergency และ report export
- การเปรียบเทียบ aggregate snapshot ก่อน-หลังในตัวชี้วัดที่มีข้อมูลจริง

### 6.2 สิ่งที่ยังไม่ใช่ "การมีส่วนร่วม" โดยตรง

กรอบปัจจุบันมี 24 metrics:

- `ready` 9 ตัว (37.5%)
- `partial` 4 ตัว (16.7%)
- ต้องเพิ่ม event/baseline/external evidence 11 ตัว (45.8%)

ตัวชี้วัดส่วนใหญ่เน้น Efficiency/Effectiveness และ system adoption ไม่ได้วัดครบวงจรว่าใครมีอิทธิพลต่อการตัดสินใจอย่างไร

เมื่อเทียบกับวงจรการมีส่วนร่วมที่ครอบคลุมการระบุปัญหา การออกแบบทางเลือก การตัดสินใจ การร่วมดำเนินงาน และการประเมินผล ระบบปัจจุบันมีภาพดังนี้:

| มิติ | ความครอบคลุมปัจจุบัน | ช่องว่าง |
|---|---|---|
| ร่วมระบุปัญหา | บางส่วน ผ่านเหตุฉุกเฉิน/คำขอ | ไม่มีช่องเสนอประเด็นทั่วไปและจัดหมวดปัญหา |
| ร่วมวางแผน/ออกแบบทางเลือก | ต่ำ | ไม่มีทางเลือก ผู้ร่วมเสนอ ความเห็น หรือการปรึกษาหารือ |
| ร่วมตัดสินใจ | บางส่วน ผ่าน approve/reject และ province decision-log | ไม่เก็บผู้ร่วมพิจารณา เหตุผล/ทางเลือกอย่างมีโครงสร้าง และ feedback loop |
| ร่วมดำเนินงาน | สูง | workflow โรงเรียน คนขับ ขนส่ง และสังกัดเชื่อมกันจริง |
| ร่วมรับประโยชน์ | ต่ำ | วัดผลบริการบางส่วน แต่ไม่เก็บ perceived benefit/equity จากผู้ปกครอง นักเรียน และผู้ใช้ |
| ร่วมติดตามและประเมินผล | บางส่วน | มี report/snapshot แต่ไม่มี stakeholder feedback, meeting evidence และ action closure ครบ |

### 6.3 กลุ่มผู้มีส่วนร่วมที่ขาด

กรอบวิจัยปัจจุบันวัด 6 login roles แต่ไม่รวม:

- ผู้ปกครอง ซึ่งเป็นผู้รับข้อมูลและผู้ร่วมรับผิดชอบความปลอดภัย
- นักเรียน ซึ่งเป็นผู้รับผลโดยตรง แม้ไม่ควรต้องมีบัญชีระบบ
- ครูบัญชีย่อย ซึ่งมีภาระและประสบการณ์ต่างจากบัญชีโรงเรียนเต็ม
- ตัวแทนผู้บริหาร/คณะทำงานหรือการประชุมที่ตัดสินใจจริง

จึงยังไม่ครอบคลุมพอที่จะสรุป "การบริหารแบบมีส่วนร่วม" ทั้งระบบ โดยไม่ใช้แบบสอบถาม สัมภาษณ์ บันทึกประชุม และหลักฐานภายนอกร่วม

## 7. ประเด็นความถูกต้องเชิงระเบียบวิธี

### Major 1: คำว่า "พร้อมประเมิน" อิงจำนวน action มากเกินไป

`EvaluationDashboard`, `ExecutiveSummary` และ `ExecutivePrint` ตีความ action รวมตั้งแต่ 20 ครั้งขึ้นไปและมี snapshot ว่า "พร้อมประเมิน" การ login/import ซ้ำจำนวนมากจึงอาจทำให้บทบาทดูพร้อม แม้ไม่มีหลักฐานการมีส่วนร่วมที่มีความหมาย

ข้อเสนอ: เปลี่ยนเป็น "มีหลักฐานระบบเบื้องต้น" และคำนวณ readiness จาก coverage ของตัวชี้วัดแต่ละมิติ ไม่ใช่ raw action count

### Major 2: Research export ระบุ readiness เกินหลักฐาน

`backend/src/routes/admin.routes.js` กำหนด `dme_mie_ready: true` แบบคงที่ ทั้งที่ 11 จาก 24 metrics ยังต้องมี event/baseline/external evidence และ production snapshot ล่าสุดหยุดที่ 20 มิถุนายน 2569

ข้อเสนอ: ส่งออก `evidence_readiness` แยก metric พร้อมสถานะ/เหตุผล/วันที่หลักฐานล่าสุด และห้ามมี boolean PASS เดียวแบบ hardcode

### Major 3: Baseline ยังไม่เพียงพอสำหรับการอ้างผลวิจัย

Production มี snapshots 7 รายการ ช่วง 11 เมษายนถึง 20 มิถุนายน 2569 และ decision logs 0 รายการ จึงยังเชื่อมเหตุและผลว่า "การบริหารดีขึ้นเพราะระบบ" ไม่ได้

ข้อเสนอ: freeze research protocol, กำหนด pre/post period, confounders, sampling, external instruments และรอบ snapshot ก่อนเริ่มเก็บผลจริง

### Major 4: ไม่มี closed feedback loop

มีคำขอและการอนุมัติ แต่ยังไม่มีโครงสร้างทั่วไปที่พิสูจน์ว่าเสียงจากโรงเรียน คนขับ ผู้ปกครอง หรือขนส่งถูกพิจารณา นำไปใช้ และแจ้งผลกลับ

ข้อเสนอ: เพิ่ม participation case/event model ใน workflow เดิม ไม่สร้างเมนูแยกจำนวนมาก

## 8. แบบข้อมูลขั้นต่ำที่ควรเพิ่ม โดยไม่ทำให้ระบบรก

ไม่ควรเพิ่มหน้าใหม่หนึ่งหน้าต่อหนึ่งตัวชี้วัด ให้เพิ่มข้อมูลกลาง 2 ชุด:

### 8.1 Participation case

ใช้กับเหตุฉุกเฉิน คำขอรถ โอนย้ายนักเรียน ข้อเสนอเชิงนโยบาย และปัญหาโรงเรียน โดยเก็บ:

- ประเด็น/ประเภท/ขอบเขตหน่วยงาน
- ผู้ริเริ่มและบทบาทผู้มีส่วนร่วม
- ทางเลือกที่เสนอและผู้ให้ความเห็น
- มติ เหตุผล ผู้มีอำนาจตัดสิน และวันที่
- ผู้รับผิดชอบ กำหนดเวลา สถานะ และผลลัพธ์
- วันที่แจ้งผลกลับผู้เสนอและสถานะปิด feedback loop

### 8.2 Participation event แบบ append-only

ใช้บันทึก `SUBMITTED`, `ACKNOWLEDGED`, `COMMENTED`, `CONSULTED`, `DECIDED`, `ASSIGNED`, `COMPLETED`, `FEEDBACK_SENT` พร้อม actor, role, timestamp และ evidence reference

หน้าจอควรฝังปุ่มเหล่านี้ใน dashboard/queue เดิม เช่น "รับทราบ", "ขอความเห็น", "มอบหมาย", "บันทึกมติ", "แจ้งผลกลับ" ไม่เพิ่มเมนูใหม่ทุก action

## 10. Logic ที่เจ้าของระบบต้องยืนยันก่อนพัฒนา

1. งานวิจัยจะนิยาม "การบริหารแบบมีส่วนร่วม" ตามมิติใด และมีกรอบทฤษฎีที่อาจารย์ที่ปรึกษาอนุมัติแล้วหรือไม่
2. ผู้ปกครอง นักเรียน ครูบัญชีย่อย และตัวแทนการประชุมอยู่ในประชากร/กลุ่มตัวอย่างหรือไม่
3. Phase 1 ผู้กดเช็กเด็กคือบัญชีโรงเรียนเต็มเท่านั้น หรือครูประจำชั้นต้องทำได้ใน grade scope
4. คำขอรายชื่อ legacy ยังมีภาระงานค้างที่ต้องรักษาหรือสามารถรวมกับ Driver Registration ได้
5. สังกัดหรือ Admin เป็นผู้อนุมัติคำขอประเภทใด เพื่อไม่ให้มี queue ซ้ำสองระดับ
6. Province readiness เป็นงานประจำของจังหวัดหรือเป็นหน้าสำหรับ Project owner/Operator เท่านั้น
7. เกณฑ์ "พร้อมประเมิน" ต้องอิง metric coverage, external evidence และ minimum period เท่าใด
8. ต้องการให้ผู้ปกครองส่ง feedback/ข้อเสนอในระบบหรือเก็บผ่านเครื่องมือวิจัยภายนอก

## 11. ลำดับปรับปรุงที่แนะนำ

1. แก้ความถูกต้องของ research readiness label และ export metadata ก่อนนำตัวเลขไปอ้างอิง
2. ยืนยันกรอบวิจัย ประชากร ตัวแปร เครื่องมือ pre/post และ evidence matrix
3. เก็บ page/action telemetry แบบ data-minimized เพื่อรู้ว่าเมนูใดถูกใช้จริง
4. รวมเมนูที่ซ้ำโดยไม่ลบ API และใช้ feature flag/redirect เพื่อ rollback ได้
5. เพิ่ม participation case/events ลง workflow เดิม
6. ทำ role UAT กับผู้แทนจริงและวัด task completion/time/error ก่อน finalize เมนู
7. เริ่มเก็บ baseline ใหม่หลัง protocol freeze และห้ามปะปนข้อมูล pilot กับผลวิจัยหลัก

## 12. ข้อสรุป

ระบบปัจจุบันเหมาะกับการบริหารงานรถรับส่งเชิงปฏิบัติการและกำกับความปลอดภัย มีการใช้งานจริงและข้อมูลเชื่อมระหว่างโรงเรียน สังกัด จังหวัด ขนส่ง คนขับ และ Admin แต่ยังไม่สมบูรณ์สำหรับสรุปผลวิจัยเรื่อง "การบริหารแบบมีส่วนร่วม" เพราะวัดการทำงานและการใช้ระบบมากกว่าการมีอิทธิพลต่อการตัดสินใจ การร่วมออกแบบ และการได้รับ feedback

แนวทางที่คุ้มค่าคือไม่เพิ่มเมนูวิจัยอีก แต่ลดทางเข้า รวมหน้าที่ซ้ำ และฝังหลักฐานการมีส่วนร่วมใน workflow ที่ผู้ใช้ทำอยู่แล้ว
