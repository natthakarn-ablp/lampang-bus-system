# ระบบแฟ้มกลางรถรับส่งและการรับรองรถ–คนขับ จังหวัดลำปาง

วันที่ออกแบบ: 22 มิถุนายน 2026  
สถานะ: แบบออกแบบได้รับความเห็นชอบในหลักการ  
เจ้าของระบบ: องค์การบริหารส่วนจังหวัด (อบจ.)  
หน่วยงานร่วมตรวจ: สำนักงานขนส่งจังหวัดลำปาง

## 1. บทสรุป

เพิ่มระบบแฟ้มกลางสำหรับรถรับส่งนักเรียน เพื่อเชื่อมข้อมูลที่เดิมกระจายอยู่ระหว่างโรงเรียน สำนักงานขนส่งจังหวัด และ อบจ. ให้รถหนึ่งคันมีข้อมูลอ้างอิงร่วมกันเพียงชุดเดียว

ระบบต้องทำงานได้โดยไม่พึ่ง DLT API ในระยะแรก เจ้าหน้าที่ขนส่งจังหวัดลำปางจะเข้าตรวจรถและบันทึกผลรับรองในระบบโดยตรง หากมีสิทธิ์ใช้ API ส่วนกลางในอนาคต จะเพิ่มเป็นแหล่งตรวจสอบอีกช่องทางหนึ่งโดยไม่เปลี่ยน workflow หลัก

หลักสำคัญคือแยกการรับรองออกเป็นสามส่วน:

1. รถคันนี้ผ่านการตรวจและเอกสารยังมีผลหรือไม่
2. คนขับคนนี้มีคุณสมบัติและได้รับอนุญาตให้ขับรถคันใดบ้าง
3. ในแต่ละรอบ ใครเป็นผู้ขับรถคันใดจริง

## 2. ปัญหาปัจจุบัน

- โรงเรียนรู้ว่ามีนักเรียนของตนใช้รถคันใด แต่ไม่เห็นสถานะตรวจสภาพล่าสุดอย่างครบถ้วน
- ขนส่งรู้ว่ารถคันใดมาตรวจ แต่ไม่รู้ว่ารถให้บริการโรงเรียนใด จำนวนผู้โดยสารเท่าไร และวิ่งในพื้นที่ใด
- อบจ. ไม่มีภาพรวมว่ารถแต่ละคันมาจากพื้นที่ใด รับนักเรียนโรงเรียนไหน จำนวนเท่าไร ใครเป็นคนขับ และผลตรวจยังมีผลหรือไม่
- คนขับต้องขอเอกสารจากโรงเรียนแล้วนำไปยื่นขนส่ง แต่ข้อมูลจากกระดาษไม่ไหลกลับมาเป็นข้อมูลกลาง
- การให้คนขับสมัครใจส่งข้อมูลเพิ่มมีโอกาสล้มเหลว เพราะผู้ปกครองและโรงเรียนมีอำนาจต่อรองต่ำ
- ระบบเดิมใช้ทะเบียนรถเป็นชื่อผู้ใช้ของคนขับ ทำให้ระบุตัวคนขับจริงไม่ได้เมื่อรถหนึ่งคันมีคนขับหลายคน
- ตาราง `vehicle_inspections` ปัจจุบันเก็บเพียงรถ วันที่ ผลตรวจ วันหมดอายุ และหมายเหตุ ยังไม่มีคำขอส่งตรวจ checklist หลักฐาน หรือสถานะ workflow

## 3. เป้าหมาย

- สร้างแฟ้มกลางหนึ่งแฟ้มต่อรถหนึ่งคัน โดยยึดทะเบียนและ canonical vehicle identity เป็นตัวป้องกันข้อมูลซ้ำ
- ให้โรงเรียนใดก็ได้ที่มีนักเรียนใช้รถคันนั้นออกเอกสารส่งตรวจจากระบบกลาง
- ให้เอกสารพิมพ์จากระบบมีเลขอ้างอิง QR และ snapshot ของข้อมูล ณ เวลาออกเอกสาร
- ให้เจ้าหน้าที่ขนส่งตรวจรถจริงและบันทึกผลในระบบโดยไม่ต้องใช้ DLT API
- ให้ อบจ. เห็นภาพรวมรถ คนขับ โรงเรียน จำนวนผู้โดยสาร จุดรับส่ง และสถานะความปลอดภัยทั้งจังหวัด
- ไม่ส่งรายชื่อนักเรียนให้ขนส่ง เพราะการตรวจมุ่งที่รถ คนขับ ความจุ และพื้นที่ให้บริการ
- รองรับคนขับหลายคนต่อรถหนึ่งคัน และคนขับหนึ่งคนได้รับอนุญาตให้ขับหลายคัน
- บันทึกคนขับจริงในแต่ละรอบ โดยไม่ต้องขออนุมัติใหม่หากอยู่ในรายชื่อที่ผ่านการตรวจล่วงหน้า
- ป้องกันรถหรือคนขับที่ไม่ผ่านเกณฑ์จากการเริ่มรอบและเช็กอินนักเรียน
- รองรับ DLT API หรือข้อมูล batch ในอนาคตผ่าน provider interface

## 4. สิ่งที่ไม่ทำในขอบเขตนี้

- ไม่ scrape เว็บไซต์หรือใช้บัญชีของเจ้าหน้าที่เพื่อดึงข้อมูลจากระบบกรมการขนส่ง
- ไม่สร้างฐานข้อมูลสำเนาของกรมการขนส่งทั้งหมด
- ไม่เปิดเผยรายชื่อนักเรียนต่อขนส่งหรือสาธารณะ
- ไม่ใช้ AI เป็นผู้ตัดสินผลตรวจสภาพรถ
- ไม่ใช้ API เป็นเงื่อนไขบังคับก่อนเปิดใช้งานระบบ
- ไม่เปลี่ยนกฎทางราชการว่ากระดาษฉบับใดเป็นเอกสารทางการ ระบบจะสร้าง PDF/QR รองรับขั้นตอนกระดาษที่ยังจำเป็น

## 5. ผู้ใช้งานและความรับผิดชอบ

### 5.1 โรงเรียน

- ดูแลข้อมูลนักเรียนของโรงเรียนตนเอง
- ผูกนักเรียนกับรถ รอบเช้า/เย็น และจุดรับส่ง
- ตรวจความถูกต้องของรถและคนขับที่ให้บริการโรงเรียน
- เปิดคำขอส่งตรวจหรือพิมพ์เอกสารกลางได้ หากรถมีนักเรียนของโรงเรียนนั้น
- เห็นผลตรวจและวันหมดอายุของรถที่ให้บริการโรงเรียน

### 5.2 เจ้าหน้าที่ขนส่งจังหวัด

- เห็นทะเบียน ประเภทรถ ความจุ เจ้าของ คนขับ โรงเรียน จำนวนผู้โดยสาร และพื้นที่ให้บริการ
- ไม่เห็นรายชื่อนักเรียนหรือข้อมูลผู้ปกครอง
- เปิดคำขอจาก QR หรือคิวรอตรวจ
- ตรวจเอกสาร ตรวจรถตาม checklist และแนบหลักฐาน
- บันทึกผลผ่าน ไม่ผ่าน ต้องแก้ไข หรือรอตรวจ
- กำหนดวันหมดอายุ เงื่อนไข และรายการที่ต้องแก้ไข
- ลงชื่อรับรองผลด้วยบัญชีเจ้าหน้าที่เฉพาะบุคคล

### 5.3 อบจ.

- เห็น dashboard ทั้งจังหวัด
- กำหนด checklist version และกฎ eligibility ร่วมกับขนส่ง
- ตรวจรายการรถไม่มาตรวจ รถหมดอายุ บรรทุกเกิน หรือมีข้อบกพร่อง
- ระงับสถานะการให้บริการตามอำนาจและระเบียบที่กำหนด
- ตรวจ audit log และจัดการข้อร้องเรียน

### 5.4 คนขับ

- ใช้บัญชีส่วนตัว ไม่ใช้ทะเบียนรถเป็นตัวตน
- ดูรถทุกคันที่ตนได้รับอนุญาตให้ขับ
- เลือกหรือสแกน QR รถก่อนเริ่มรอบ
- ยืนยันว่าเป็นผู้ขับจริงในรอบนั้น
- ทำ pre-trip check และส่งตำแหน่ง GPS ตาม workflow เดิม

### 5.5 ผู้ปกครองและสาธารณะ

- เห็นเฉพาะทะเบียน ประเภทรถ สถานะรับรอง ผลตรวจโดยสรุป และวันหมดอายุผ่าน QR
- ไม่เห็นเจ้าของรถ ที่อยู่ เลขบัตรประชาชน เลขตัวถังเต็ม เอกสารต้นฉบับ หรือประวัติที่เป็นข้อมูลอ่อนไหว

## 6. แฟ้มกลางรถรับส่ง

รถหนึ่งคันมีแฟ้มกลางประกอบด้วย:

- รหัสรถและทะเบียนแบบ canonical
- ประเภท ยี่ห้อ รุ่น ปีรถ และความจุที่รับรอง
- เจ้าของรถและข้อมูลติดต่อที่จำกัดสิทธิ์การเข้าถึง
- คนขับหลักและคนขับสำรองที่ได้รับอนุญาต
- โรงเรียนทั้งหมดที่ให้บริการ
- จำนวนผู้โดยสารแยกโรงเรียน รอบเช้า และรอบเย็น
- จุดรับส่งและพื้นที่เส้นทาง
- ภาษี พ.ร.บ. ประกัน และวันหมดอายุ
- คำขอส่งตรวจ เอกสาร PDF และ QR
- checklist ผลตรวจ หลักฐาน และเงื่อนไขแก้ไข
- ประวัติการรับรอง ระงับ ต่ออายุ และแก้ไขข้อมูล
- รอบปฏิบัติงานและคนขับจริงในแต่ละรอบ

## 7. เอกสารกลางและการรวมข้อมูลหลายโรงเรียน

- รถหนึ่งคันมีคำขอเปิดอยู่ได้หนึ่งคำขอต่อรอบการตรวจ
- โรงเรียนใดก็ได้ที่มีนักเรียนผูกกับรถสามารถเปิดคำขอหรือพิมพ์เอกสาร
- โรงเรียนที่กดพิมพ์เป็น `issuing_school` เท่านั้น ไม่ได้รับรองข้อมูลแทนโรงเรียนอื่น
- รายการโรงเรียนและจำนวนผู้โดยสารดึงจากข้อมูลปัจจุบันในระบบกลาง
- ข้อมูลนักเรียนแต่ละรายการยังอยู่ภายใต้ scope ของโรงเรียนต้นทาง
- เอกสารแสดงจำนวนผู้โดยสารแยกตามโรงเรียนและรอบ แต่ไม่แสดงรายชื่อ
- เอกสารมีเลขคำขอ QR เวอร์ชัน วันเวลาออก และแหล่งข้อมูลของแต่ละโรงเรียน
- เมื่อข้อมูลสำคัญเปลี่ยนหลังออกเอกสาร เช่น จำนวนผู้โดยสาร โรงเรียน คนขับ หรือรถ ระบบสร้างเวอร์ชันใหม่และทำเครื่องหมายฉบับเดิมว่า `SUPERSEDED`
- QR ชี้ไปยังสถานะล่าสุด ส่วน PDF เก็บ snapshot เพื่อพิสูจน์ข้อมูล ณ เวลาออกเอกสาร

## 8. Workflow การส่งตรวจ

### 8.1 สร้างคำขอ

1. โรงเรียนค้นหารถจากทะเบียน
2. ระบบรวมข้อมูลรถ โรงเรียน จำนวนผู้โดยสาร จุดรับส่ง และคนขับที่ได้รับอนุญาต
3. ระบบตรวจข้อมูลจำเป็นและความจุเบื้องต้น
4. โรงเรียนยืนยันและสร้างคำขอ
5. ระบบออก PDF และ QR สำหรับนำไปยื่นขนส่ง

### 8.2 ตรวจโดยขนส่ง

1. เจ้าหน้าที่เปิดคิวหรือสแกน QR
2. ระบบแสดงข้อมูลที่จำเป็นโดยไม่เปิดรายชื่อนักเรียน
3. เจ้าหน้าที่ตรวจเอกสารและตัวรถตาม checklist version ที่มีผล
4. เจ้าหน้าที่แนบภาพหรือเอกสารหลักฐานตามข้อกำหนด
5. เจ้าหน้าที่บันทึกผล `PASSED`, `FAILED`, `NEEDS_FIX` หรือ `PENDING`
6. ระบบบันทึกผู้ตรวจ วันเวลา ผล เงื่อนไข และวันหมดอายุแบบ append-only event
7. โรงเรียนและ อบจ. ได้รับผลทันที

### 8.3 การแก้ไขและตรวจซ้ำ

- ผล `NEEDS_FIX` ระบุรายการแก้ไขและกำหนดเวลา
- การยื่นตรวจซ้ำสร้าง inspection attempt ใหม่ ไม่แก้ทับผลเดิม
- ผล `FAILED` หรือพ้นกำหนดแก้ไขทำให้รถไม่ผ่าน eligibility
- การแก้ข้อมูลรถที่มีผลต่อความปลอดภัย เช่น ความจุ ประเภทรถ หรือ canonical identity ต้องส่ง review ใหม่

## 9. Checklist การตรวจ

Checklist ต้องกำหนดเป็น template versioned เพื่อให้ขนส่งและ อบจ. ปรับตามระเบียบได้โดยไม่แก้โค้ดทุกครั้ง หมวดขั้นต่ำ ได้แก่:

- ยืนยันทะเบียน เลขตัวถัง และตัวรถตรงกัน
- ประเภทและความจุรถ
- เบรก ยาง ไฟ กระจก และอุปกรณ์พื้นฐาน
- ประตู ทางออกฉุกเฉิน เข็มขัดนิรภัย และอุปกรณ์ดับเพลิง
- สภาพที่นั่งและพื้นที่โดยสาร
- ภาษี พ.ร.บ. ประกัน และเอกสารที่เกี่ยวข้อง
- ข้อบกพร่อง ระดับความรุนแรง หลักฐาน และเงื่อนไขแก้ไข

กฎที่เป็นข้อบังคับต้องกำหนดจากแบบตรวจของขนส่งจังหวัด ไม่ใช้รายการนี้แทนระเบียบราชการ

## 10. คนขับหลัก คนขับสำรอง และหลายรถ

### 10.1 แฟ้มคนขับ

- ตัวตนและบัญชีผู้ใช้เฉพาะบุคคล
- รูปและข้อมูลติดต่อ
- ประเภทใบขับขี่ เลขอ้างอิง วันออก และวันหมดอายุ
- สถานะ `VERIFIED`, `EXPIRING`, `EXPIRED`, `SUSPENDED`
- ประวัติการอนุมัติ ระงับ และเหตุการณ์สำคัญ

### 10.2 ความสัมพันธ์คนขับ–รถ

- รถหนึ่งคันมีคนขับหลักหนึ่งคนและคนขับสำรองหลายคนได้
- คนขับหนึ่งคนอยู่ในรายชื่อรถหลายคันได้
- ความสัมพันธ์แต่ละรายการมีบทบาท `PRIMARY` หรือ `BACKUP`, วันเริ่ม วันสิ้นสุด และสถานะ
- คนขับที่ใบขับขี่หมดอายุหรือถูกระงับถูกตัดสิทธิ์จากรถทุกคันโดยอัตโนมัติ
- การเพิ่มคนขับใหม่เข้า pool ต้องตรวจคุณสมบัติก่อน ไม่อนุญาตให้เพิ่มย้อนหลังหลังเริ่มรอบ

### 10.3 การเริ่มรอบ

1. คนขับล็อกอินด้วยบัญชีส่วนตัว
2. เลือกหรือสแกน QR รถที่ตนได้รับอนุญาต
3. เลือกรอบเช้าหรือเย็นและกดเริ่มปฏิบัติงาน
4. ระบบตรวจรถ คนขับ ความสัมพันธ์ และ conflict แบบ transaction
5. เมื่อผ่าน ระบบสร้าง operating shift และผูก GPS, check-in, emergency และ audit กับคนขับจริง
6. คนขับกดจบรอบเมื่อปฏิบัติงานเสร็จ

ไม่ต้องขออนุมัติใหม่ทุกครั้งหากคนขับอยู่ใน pool และเอกสารยังมีผล

## 11. กฎ Eligibility

รถมีสถานะ `ELIGIBLE` เมื่อครบทุกเงื่อนไข:

- ผลตรวจล่าสุดเป็น `PASSED` และยังไม่หมดอายุ
- เอกสารบังคับยังมีผล
- ไม่มีสถานะระงับหรือข้อบกพร่องร้ายแรงค้างอยู่
- ความจุที่รับรองไม่น้อยกว่าจำนวนผู้โดยสารสูงสุดของรอบเช้าหรือเย็น
- มีคนขับที่ได้รับอนุญาตอย่างน้อยหนึ่งคนและยังมีคุณสมบัติครบ

การเริ่ม operating shift ต้องตรวจเพิ่มเติมว่า:

- คนขับปัจจุบันอยู่ใน pool ของรถ
- ใบขับขี่ยังมีผลและประเภทถูกต้อง
- คนขับไม่มี shift อื่นที่ยังเปิดอยู่
- รถไม่มี shift อื่นในรอบเวลาเดียวกัน
- รถยังไม่ถูกระงับหลังจากคำนวณ eligibility ล่าสุด

ไม่มี emergency override สำหรับใบขับขี่หมดอายุ คนขับถูกระงับ หรือรถตรวจไม่ผ่าน

## 13. แบบข้อมูลเชิงแนวคิด

การ implementation ใช้ additive migrations เพื่อรักษาข้อมูลเดิม โครงสร้างที่ต้องมี:

- `vehicle_inspection_applications` — คำขอส่งตรวจและสถานะ
- `inspection_application_schools` — โรงเรียนและจำนวนผู้โดยสารใน snapshot
- `inspection_application_routes` — รอบ พื้นที่ และจุดรับส่งโดยสรุป
- `inspection_checklist_templates` — แบบตรวจ versioned
- `inspection_checklist_items` — รายการตรวจในแต่ละ version
- `inspection_attempts` — การตรวจแต่ละครั้ง
- `inspection_results` — ผลรายข้อและระดับความรุนแรง
- `inspection_evidence` — หลักฐานที่มี access control
- `driver_qualifications` — ใบขับขี่และสถานะคุณสมบัติ
- `driver_vehicle_assignments` — ใช้ตารางเดิมและเพิ่มบทบาท validity และสถานะตามความจำเป็น
- `vehicle_operating_shifts` — คนขับจริง รถ รอบ และช่วงเวลา
- `verification_events` — timeline แบบ append-only

ตาราง `vehicle_inspections` เดิมยังใช้เป็นผลสรุปล่าสุดเพื่อ compatibility โดยรายละเอียดใหม่อยู่ในตารางเฉพาะด้าน

## 14. การเข้าสู่ระบบคนขับ

ทะเบียนรถต้องไม่เป็นตัวตนหลักของผู้ใช้หลัง migration เพราะ:

- รถหนึ่งคันมีคนขับหลายคน
- คนขับหนึ่งคนขับหลายรถ
- audit ต้องระบุตัวคนขับจริง
- การแชร์รหัสผ่านทะเบียนรถทำให้เพิกถอนสิทธิ์รายบุคคลไม่ได้

แนวทาง migration:

1. สร้างบัญชีรายบุคคลให้คนขับเดิม
2. ผูกบัญชีกับ `drivers.id`
3. ย้ายความสัมพันธ์รถเดิมเข้าสู่ driver pool
4. บังคับตั้งรหัสผ่านส่วนตัวหรือใช้ช่องทางยืนยันตัวตนที่อนุมัติ
5. ปิด plate-based login เมื่อบัญชีในพื้นที่ได้รับการย้ายครบตามแผน rollout

## 15. สิทธิ์ข้อมูลและ PDPA

- ขนส่งเห็นเฉพาะข้อมูลที่จำเป็นต่อการตรวจรถ คนขับ ความจุ จำนวนผู้โดยสาร และพื้นที่ให้บริการ
- ขนส่งไม่เห็นชื่อ รหัสนักเรียน เบอร์ผู้ปกครอง หรือข้อมูลเช็กอินรายคน
- โรงเรียนเห็นรายชื่อนักเรียนเฉพาะโรงเรียนตนเอง
- อบจ. เห็นข้อมูลตามภารกิจและสิทธิ์ที่ได้รับอนุมัติ
- สาธารณะเห็นเฉพาะข้อมูลสรุปความปลอดภัย
- เอกสารต้นฉบับและภาพหลักฐานไม่เปิดผ่าน public QR
- การเข้าถึงข้อมูลละเอียดบันทึก audit log
- ข้อความ privacy notice และฐานการประมวลผลต้องระบุ อบจ. เป็นเจ้าของระบบ/ผู้ควบคุมข้อมูลให้ตรงข้อเท็จจริง และผ่านการทบทวนของ DPO/ฝ่ายกฎหมาย
- การยินยอมใช้เฉพาะข้อมูลหรือการเปิดเผยที่เป็นทางเลือก ไม่ใช้ consent เป็นกลไกหลักเพื่อบังคับมาตรฐานความปลอดภัย

## 16. QR และเอกสาร PDF

### 16.1 QR บนหนังสือส่งตรวจ

- เป็น opaque revocable token
- เปิดรายละเอียดคำขอให้เฉพาะบัญชีขนส่ง โรงเรียน หรือ อบจ. ตามสิทธิ์
- แสดงสถานะล่าสุดและแจ้งเมื่อเอกสารฉบับที่สแกนถูกแทนที่

### 16.2 QR ประจำรถ

บุคคลทั่วไปเห็น:

- ทะเบียนและประเภทรถ
- สถานะรับรอง
- วันที่ตรวจล่าสุดและวันหมดอายุ
- สถานะประกัน/เอกสารโดยสรุป
- ช่องทางแจ้งปัญหาหรือเหตุฉุกเฉิน

เจ้าหน้าที่ที่ล็อกอินแล้วเห็นข้อมูลเพิ่มเติมตาม role

## 17. การแจ้งเตือน

- โรงเรียนและ อบจ. เมื่อขนส่งบันทึกผล
- คนขับและโรงเรียนเมื่อรถหรือใบขับขี่ใกล้หมดอายุ
- โรงเรียนเมื่อจำนวนผู้โดยสารเกินความจุ
- อบจ. เมื่อรถไม่มาตรวจ ตรวจไม่ผ่าน หรือหมดอายุแล้วยังมีนักเรียนผูกอยู่
- ผู้เกี่ยวข้องเมื่อสถานะรถถูกระงับ
- โรงเรียนเมื่อมีคนขับที่ไม่ได้รับอนุญาตพยายามเริ่มรอบ

## 18. Error handling และกฎความถูกต้อง

- ใช้ canonical plate ป้องกันรถซ้ำแม้รูปแบบเว้นวรรคต่างกัน
- หนึ่งรถมีคำขอ active ต่อรอบตรวจได้เพียงหนึ่งรายการ
- การเริ่ม shift ใช้ transaction/locking ป้องกันคนขับหรือรถเปิดสองรอบพร้อมกัน
- ผลตรวจและการเปลี่ยนสถานะเก็บเป็น event ใหม่ ไม่แก้ประวัติเดิม
- หากข้อมูลโรงเรียนเปลี่ยนระหว่างตรวจ ระบบเก็บ snapshot เดิมและแจ้งว่ามีข้อมูลใหม่รอ review
- หากไฟล์หลักฐานอัปโหลดไม่สำเร็จ ห้าม finalize ผลตรวจที่กำหนดหลักฐานเป็น required
- หากระบบภายนอกหรือ provider ใช้งานไม่ได้ workflow manual ยังคงทำงานได้
- การคำนวณ eligibility ต้องทำซ้ำเมื่อผลตรวจ เอกสาร ความจุ จำนวนผู้โดยสาร คนขับ หรือสถานะระงับเปลี่ยน

## 19. Provider interface สำหรับอนาคต

กำหนดแหล่งยืนยันเป็น provider ที่เปลี่ยนได้:

- `DLT_OFFICER` — เจ้าหน้าที่ขนส่งตรวจและบันทึกโดยตรง
- `PAO_INSPECTOR` — เจ้าหน้าที่ อบจ. ตรวจในขอบเขตที่ได้รับมอบหมาย
- `PRIVATE_INSPECTION_CENTER` — สถานตรวจสภาพที่ได้รับอนุญาต
- `SIGNED_BATCH_FILE` — ไฟล์ที่แลกเปลี่ยนภายใต้ข้อตกลง
- `DLT_CENTRAL_API` — ช่องทางส่วนกลางในอนาคต

ทุก provider ส่งผลในรูปแบบมาตรฐานเดียวกัน เช่น source, reference number, verified fields, result, checked time, expiry, evidence และ verifier identity ทำให้เพิ่ม API ภายหลังได้โดยไม่เปลี่ยนหน้าจอหรือ workflow หลัก

## 20. การทดสอบและเกณฑ์ยอมรับ

### 20.1 Workflow

- โรงเรียนใดก็ได้ที่มีนักเรียนใช้รถสามารถสร้างและพิมพ์คำขอกลางได้
- โรงเรียนที่ไม่มีความเกี่ยวข้องกับรถสร้างคำขอไม่ได้
- รถหลายโรงเรียนแสดงจำนวนผู้โดยสารถูกต้องโดยไม่เปิดรายชื่อให้ขนส่ง
- QR เปิดคำขอและแสดงเวอร์ชันล่าสุดได้
- ผลตรวจใหม่ไม่ทำลายประวัติเดิม

### 20.2 คนขับหลายรถ

- รถหนึ่งคันมีคนขับหลายคนได้
- คนขับหนึ่งคนอยู่ใน pool ของหลายรถได้
- คนขับใน pool เริ่มรอบได้โดยไม่ขออนุมัติใหม่
- คนขับนอก pool ถูกปฏิเสธ
- ใบขับขี่หมดอายุทำให้เริ่มรอบไม่ได้ทุกคัน
- concurrency test ยืนยันว่าคนเดียวหรือรถเดียวเปิดสอง shift พร้อมกันไม่ได้

### 20.3 ความปลอดภัยและสิทธิ์ข้อมูล

- ขนส่งไม่สามารถเรียกข้อมูลรายชื่อนักเรียนผ่าน UI หรือ API
- public QR ไม่เปิด PII หรือไฟล์หลักฐาน
- ทุกการดูข้อมูลละเอียดและการบันทึกผลมี audit log
- token ที่ revoke แล้วใช้เปิด QR ไม่ได้
- ไฟล์หลักฐานผ่านการตรวจชนิด ขนาด และ authorization

### 20.4 Eligibility

- รถผ่านตรวจแต่เอกสารหมดอายุเป็น `INELIGIBLE`
- รถเอกสารครบแต่ตรวจไม่ผ่านเป็น `INELIGIBLE`
- จำนวนผู้โดยสารเกินความจุเป็น `INELIGIBLE`
- รถและคนขับผ่านครบจึงเริ่มรอบได้

## 21. แผน rollout

### Phase 1 — แฟ้มรถและการตรวจร่วม

- คำขอส่งตรวจกลาง
- PDF/QR
- คิวเจ้าหน้าที่ขนส่ง
- checklist versioned และหลักฐาน
- eligibility และ dashboard อบจ./โรงเรียน

### Phase 2 — บัญชีคนขับรายบุคคล

- driver qualifications
- driver pool หลายคนต่อหลายรถ
- operating shift และการผูกคนขับจริง
- migration ออกจาก plate-based login

### Phase 3 — การบังคับใช้และแจ้งเตือน

- expiry automation
- capacity alerts
- suspension workflow
- complaint/reinspection workflow
- รายงานระดับจังหวัด

### Phase 4 — การเชื่อมข้อมูลภายนอก

- signed batch exchange หากได้รับอนุญาต
- DLT Central API adapter หากได้รับ key ในอนาคต
- reconciliation โดยไม่เปลี่ยน workflow หลัก

## 22. ผลลัพธ์ที่คาดหวัง

- โรงเรียนเห็นว่ารถที่นักเรียนใช้อยู่ผ่านตรวจหรือไม่
- ขนส่งเห็นบริบทการให้บริการของรถก่อนตรวจโดยไม่ต้องเห็นรายชื่อนักเรียน
- อบจ. มีภาพรวมรถรับส่งทั้งจังหวัดและติดตามความเสี่ยงได้
- ผู้ปกครองตรวจสถานะความปลอดภัยจาก QR ได้
- ระบบระบุตัวคนขับจริงในแต่ละรอบได้ แม้มีคนขับสำรองและสลับรถ
- กระบวนการทำงานได้ทันทีโดยไม่มี DLT API และพร้อมเพิ่มการเชื่อมต่อในอนาคต
