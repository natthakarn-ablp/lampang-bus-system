# Workflow ตรวจสอบสิทธิ์ขนส่ง

ใช้เอกสารนี้ก่อนเผยแพร่ทุกครั้งที่แก้เมนูขนส่ง, route, role guard, รายงาน, เอกสารรถ/คนขับ หรือขั้นตอนตรวจรับรองรถ เป้าหมายคือยืนยันจากระบบจริงทั้งสี่ชั้น: เมนูที่เห็น, สิทธิ์ API ฝั่ง server, ขอบเขตข้อมูล และ audit log

## ขอบเขตสิทธิ์ที่ต้องได้

| หมวด | ขนส่งทำได้ | เงื่อนไข |
|---|---|---|
| ดู | ภาพรวมรถ รายการรถ รถรอตรวจ/ใกล้หมดอายุ ผลตรวจ คิวรับรอง timeline checklist คนขับและเอกสารที่เกี่ยวข้อง | แผนที่เป็นข้อมูลรวม; เปิดเอกสารต้องบันทึก audit สำเร็จก่อนส่งไฟล์ |
| แก้ไข | เพิ่มรถเพื่อเข้ากระบวนการตรวจ บันทึก/แก้/ลบผลตรวจเดิมตาม ownership มอบหมายคนขับ ตรวจคุณสมบัติ และ review เอกสาร | ห้ามแก้ข้อมูลนักเรียน ผู้ใช้ หรือข้อมูลต้นทางของโรงเรียน |
| อนุมัติ | เริ่มครั้งตรวจ ลง checklist สรุปผล และยกเลิกงานที่ตนเริ่ม | เริ่มซ้ำต้องถูกปฏิเสธ; เจ้าหน้าที่อื่นสรุปหรือยกเลิกแทนไม่ได้ ยกเว้น admin |
| ส่งออก | CSV เฉพาะข้อมูลรถและผลตรวจ | ไม่มีข้อมูลนักเรียน ผู้ปกครอง เบอร์โทร หมายเหตุ หรือไฟล์หลักฐาน; audit ล้มเหลวต้องไม่ปล่อยไฟล์ |
| ต้องถูกปฏิเสธ | รายงานทั่วไป ข้อมูล/รายการเขียนของโรงเรียน งานคนขับ/เช็กชื่อ และจัดการผู้ใช้ | ต้องบังคับที่ server แม้ผู้ใช้พิมพ์ URL หรือเรียก API เอง |

ฟีเจอร์ QR เป็นสิทธิ์ตามเงื่อนไข `FEATURE_VEHICLE_QR`; การที่ route มี guard ไม่ได้แปลว่าฟีเจอร์เปิดใน production ต้องบันทึกค่าจริงแยกทุกครั้ง

## ขั้นตอนตรวจ

1. **ตรึงรุ่นและสภาพระบบ** — บันทึก commit, เวลา, ค่า feature flags ที่เกี่ยวข้อง, health, DB connectivity และยืนยันว่าไม่มี deploy lock ห้ามเริ่มชุดทดสอบเขียนบน production
2. **ตรวจสัญญาสิทธิ์จาก route จริง** — ที่โฟลเดอร์ `backend` รัน `npm run audit:transport-permissions` ผลต้องเป็น `PASS` และ findings เป็นศูนย์ สคริปต์ mount router ทุก feature เพื่อตรวจ guard โดยไม่ต่อฐานข้อมูล
3. **รันทดสอบขอบเขตข้อมูล** — รันชุด `transportPermissionWorkflow`, `transportRoleSafety`, `transportExportRoute`, `documentExportAudit`, `vehicleVerificationDriverScope` ผลต้องผ่านทั้งหมด
4. **ตรวจเมนู** — บัญชีขนส่งต้องเห็น ภาพรวม, ตรวจรับรองรถ, บันทึกตรวจสภาพ และแผนที่จุดรับส่ง ต้องไม่เห็นเมนูนักเรียน เช็กชื่อ รายงานทั่วไป หรือจัดการผู้ใช้
5. **ตรวจ API ปฏิเสธ** — ใช้ฐานจำลองและบัญชีทดสอบขนส่งเรียก `/api/reports/*`, `/api/school/*`, `/api/driver/*`, `/api/admin/users*`; ทุกคำขอต้อง 403/404 ตามสัญญาและไม่มีข้อมูลตอบกลับ
6. **ตรวจงานจริงในฐานจำลอง** — ใช้รถ/คำขอจำลองใหม่หนึ่งชุดเท่านั้น: เปิดคิว, เริ่มตรวจ, ทดสอบเริ่มซ้ำ 409, ลง checklist, ทดสอบเจ้าหน้าที่คนอื่นสรุปไม่ได้, สรุปผล, ตรวจ timeline และ audit ห้ามใช้รถจริงหรือ replay fixture เดิม
7. **ตรวจการส่งออก** — CSV ต้องมีเฉพาะคอลัมน์ allowlist ของรถ/ผลตรวจ, neutralize สูตร spreadsheet, `Cache-Control: no-store` และมี audit `EXPORT`; จำลอง audit ล้มเหลวแล้วต้องไม่ได้ไฟล์
8. **ตรวจเอกสาร** — เปิดเอกสารที่บัญชีทดสอบมีสิทธิ์และตรวจ audit; จำลอง audit ล้มเหลวแล้วต้องไม่มี header/byte ของไฟล์หลุดออกมา ตรวจข้าม scope ต้อง 404
9. **ตรวจ production แบบอ่านอย่างเดียว** — หลังเผยแพร่ ตรวจ health, commit, PID/restart, lock, หน้าเว็บ 200, API ไม่เข้าสู่ระบบ 401 และเปิดเมนูด้วยบัญชีขนส่งจริง ห้ามสร้าง/แก้/สรุปผลรถจริงเพื่อทดสอบ
10. **บันทึกข้อขัดแย้ง** — หากข้อมูลสองแหล่งไม่ตรง ให้ระบุรถแบบรหัสภายใน, ฟิลด์, แหล่งข้อมูลและผู้รับผิดชอบ ตรวจเอกสารต้นฉบับก่อนแก้ ห้ามเลือกค่าที่ดูใหม่กว่าหรือแก้ฐานข้อมูลตรง

## เกณฑ์ผ่าน

- สคริปต์ contract และ focused tests ผ่านทั้งหมด ไม่มี transport route หลุดเข้าเขตต้องห้าม
- การเปิดเอกสารและส่งออก fail closed เมื่อ audit ใช้งานไม่ได้
- งานอนุมัติบังคับ ownership, สถานะ และการป้องกันงานซ้ำฝั่ง server
- หน้าจอ 375px ใช้งานได้ ไม่มีปุ่มที่ server จะปฏิเสธแสดงแก่ขนส่ง
- ผู้รับผิดชอบบทบาทขนส่งตรวจรับเมนูและภาษาหน้าจอจริง โดยระบุชื่อ/วันที่/ข้อสังเกตเอง
